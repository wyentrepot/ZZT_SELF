# REQS-0030 — 并发抄表深化应用（侦听台识别统计 + 模拟集中器下发，网络层/应用层分层）

> 状态：✅ P0-P4 已完成（真机验收预留，见 TODO/DONE 遗留）
> 创建：2026-09-13（2026-09-13 修订职责边界）
> 关联：REQS-0027（simcon 滑窗并发+统计表格，能力来源）、REQS-0021（AI 任务门面 v2）、
> REQS-0009（侦听台 trace）、REQS-0024/0026（网络层组网观测）、REQS-0028（recipes）

## 1. 背景与问题

知识库新增蒸馏文件已入库（附件6 HPLC 技术应用手册 V2.7 → 业务层 80-87 + 协议层 88-95 共 16 张；
CCO实现逻辑/02-并发抄表 等卡）。蒸馏卡明确了并发抄表（AFN=F1H-F1 高频采集）的业务约束：

- 同一块表未回复前不能再发第二条（否则否认 111）→ 重复下发需识别与统计
- 并发帧数上限（否认 109，CCO 侧 concurrent_tab[20]）→ 最大并发数是核心参数
- 645 类单帧数据项 ≤13 条（否认 110）
- 失败帧回空载荷、只上报成功帧 → 统计口径要区分"下发成功"与"抄读成功"

现有两处能力各有缺口：

1. **侦听台（apps/listener）**：能识别并发抄表帧（test_concurrent_meter_e2e）、trace 三段证据链、
   组网观测，但**只是识别流程，不做下发**（用户明确边界）；统计没有时间周期维度。
2. **模拟集中器（libs/sim_concentrator，REQS-0027）**：已有 batch.py 滑窗并发调度 +
   readings 统计表格 + expect_rules，但偏协议级工具：没有档案→在网→勾选的业务化工作流，
   统计**没有时间周期维度**（不能按 15 分钟周期出统计）。

用户诉求：模拟侦听台**不能只按协议下发**，要像真实使用一样分步走业务流程；
且在侦听台使用过程中对并发抄表做**周期性统计**。

## 2. 职责边界（用户明确）

- **侦听台 = 只做识别流程**：识别、解析、观察、统计，**不做任何下发**。
- **模拟集中器 = 负责深化应用部分的集中器帧下发**（1376.2）。
- **深化应用分两层**：
  - **网络层深化**：组网/信标/节点状态等（已由 REQS-0024/0026 组网观测承载，本需求不重复建设，仅按需衔接）；
  - **应用层深化**：对应集中器，1376.2 协议——档案/在网/并发抄表下发与统计，由模拟集中器承载。

## 3. 需求内容（用户原话归纳）

### 3.1 模拟集中器：向导式深化应用流程（应用层，1376.2）

1. **查档案信息** → 右侧界面出现模块表格（多少个模块、地址、协议类型等列）
2. **查在网信息** → 表格增加"在网状态"列（在线/离线）
3. **勾选下发** → 支持按协议类型勾选、按在网状态勾选（如"仅在线 + 645-07"）
4. **下发并发抄表** → 可设置最大并发数（对照 CCO 上限 20 / 否认 109）
5. **统计展示** → 下发后进入统计视图

### 3.2 周期性统计（侦听台观察侧与模拟集中器下发侧同口径）

按每个 15 分钟周期（默认，周期长度可指定）滚动统计：

| 指标 | 口径 |
|------|------|
| 最大并发数 | 周期内同时在飞帧数的峰值（滑窗在飞上限实况） |
| 成功数 / 成功率 | 抄读成功（有应答载荷）÷ 下发总数 |
| 平均耗时 | 下发→收到应答（或超时）的单帧平均时长 |
| 重复下发次数 | 同一表地址在上一次未结清（超时/未回）前再次下发的次数 |

- **侦听台侧统计**：从识别到的并发抄表帧流（trace/帧库）按周期聚合——不参与下发，
  只对"看到"的流量出统计；与模拟集中器侧同口径，便于比对（真集中器 vs 模拟）。
- **模拟集中器侧统计**：对本端下发的滑窗并发任务按周期聚合。

### 3.3 业务化而非纯协议化

下发入口、参数、结果都要用人话/业务口径呈现（复用 0027 的否认码人话、
统一抄读表格模式），AI 控制面（ai-control-plane）同步暴露对应有界接口。

## 4. 方案要点（待评审）

- **下发能力复用**：模拟集中器沿用/增强 `libs/sim_concentrator/batch.py` 滑窗调度，
  向导式流程是其上的业务封装（档案查询、在网查询、勾选过滤、并发数设置）。
- **周期统计**：新增时间桶（15min 可配）聚合，模拟集中器侧沿用 0027 readings 存储加周期字段；
  侦听台侧从 trace/帧库按 AFN=F1 并发抄表事件周期聚合（只读）。
  统计端点：simcon `GET /api/simcon/batch/stats?period=15m`；侦听台
  `GET /api/listener/concurrent/stats?period=15m`（只读识别）。
- **蒸馏知识挂钩**：否认 109/110/111 人话解释与并发上限默认值取自蒸馏卡
  （CCO实现逻辑/02-并发抄表、业务层 80-87），不硬编码 magic number。
- **网络层衔接**：在网状态可复用网络层组网观测（REQS-0024/0026）的节点在线判定结果，
  避免应用层另算一套在网口径。

## 9. 真实样本实测验证与口径修正（2026-09-13）

测试数据：`测试文件/并发抄表-测试文件/原始报文自动保存 - 2026-06-30.txt`
（303MB 空口全天抓包，用户补回）。DLL 全量解析 87,355 帧并发抄表帧
（下发请求 83,747 + 电表应答 3,598，510 块表，约 9.8 小时）零错误回放进
frame_log 副本；独立实现与被测实现按 15m/30s/1h 三周期（1,220 桶）逐桶对拍
四指标全一致；真实 HTTP 端点 `GET /api/concurrent/stats` 200 与函数级一致。
工具留存 output/req30_verify/（未入库）。

实测发现并修复：
1. **P1 重复下发恒 0**：collect_attempts 在重发时把旧尝试按当刻超时结清，
   period_stats 的 open_until 判据永不成立 → listener 侧 duplicate_count 结构性
   漏计（真实流量 81,265 次重发全为 0）。修复：重发产生的尝试带显式 duplicate
   标记，aggregate 透传计数（simcon 下发侧无标记，行为不变）。
2. **P1 带地址域帧成败判定失效**：concurrent_readonly._payload 硬编码偏移 13
   （无地址域布局），真实下发帧（batch.py 带地址构帧）切位错误。修复：按解析
   结构的 地址域A 长度定位 AFN，旧切法降级为回退路径。
3. **P2 长度域字节序**：数据单元长度按 02 卡代码口径取低字节在前
   （datalen=(buff[3]<<8)+buff[2]）；concurrent_match（读）与 batch.py（写）
   由大端改为小端。判成败不受字节序影响。
4. **口径更正**：AFN=F1H-F1H/FN=F1H 写法是 journal F{n} 渲染被误读，
   线上真值 Fn=1（DT=01 00）；88 号卡不存在于知识库，识别口径引用改为
   《CCO实现逻辑/02-并发抄表》。simcon F1 下发数据单元字节序未在实机验证过
   （docs/18 实机验收止步于 03H-F4），真机验收时需一并确认。
