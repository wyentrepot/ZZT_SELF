# 工作台主题系统评估报告（七维度诊断）

> 评估日期：2026-08-30
> 评估范围：主题层（`tokens.css` 349 行）+ 外壳组件样式（`styles.css` 292 行）+ 9 个页面的内嵌样式
> 评估方法：静态代码审计 + WCAG 2.1 对比度实测（`_tmp_theme_audit/contrast.py`）
> 关联：REQS-0010 P5（主题统一，挂起待决策）、REQS-0011（UI 重设计 Demo，P0-P2 已完成）

## 0. 一句话结论

**「丑」是症状，「死」是病灶，而真正的病根是：主题系统在物理上只覆盖了 3/9 的页面。**

切换主题时，变化的只有顶部 header 和左侧侧栏；点进侦听台、模块日志、报文追踪、协议字典、场景脚本、模拟集中器这 6 个页面，**配色纹丝不动**。
这不是风格偏好问题，是**架构分叉**问题——改配色属于审美，改架构属于工程。

## 1. 核心事实：三套互不兼容的 Token 方言

代码里存在 **3 套命名体系完全不同、主色也各不相同**的 CSS 变量方言。

| 方言 | 覆盖范围 | 命名体系 | 主色 | 文件 |
|------|----------|----------|------|------|
| **A · 工作台** | 外壳 + 验证工作台 + 串口配置 + 工作台状态 | `--bg-page` / `--fg-default` / `--accent` | `#06b6d4` 青蓝 | `tokens.css` |
| **B · 设计稿系** | 报文追踪 + 协议字典 + 场景脚本 + 模拟集中器 | `--bg-0..4` / `--tx-1..4` / `--ac` | `#22d3ee` 亮青 | 各页内嵌 `<style>` |
| **C · 侦听台系** | 侦听台 + 模块日志 | `--canvas` / `--panel` / `--ink` / `--cyan` | `#45e0c2` 青绿 | `styles.css`（页面私有） |

**证据链：**

- 全仓共 **7 处 `:root {}` 定义**（`tokens.css:7`、`dict.html:9`、`trace.html:9`、`scenario.html:8`、`simcon.html:8`、`listener/styles.css:1`、`module-serial/styles.css:1`）
- 引用 `tokens.css` 的文件只有 **5 个**：`index.html`、`styles.css`、`workbench.html`、`maintenance.html`、`serial-profile.html`
- 但使用 `var(--*)` 的文件有 **17 个** —— 其余 12 个用的是自己那套方言的变量

**为什么三种"青"是致命的：**
`#06b6d4`、`#22d3ee`、`#45e0c2` 在色相环上分别偏蓝、偏亮、偏绿。人眼对这种细微色差极其敏感——用户说不出"哪里怪"，但会本能地判断"不精致、凑出来的"。这就是「丑」的物理来源。

### 维度 1 · 视觉一致性 — 3/10

**现状证据**

### 维度 2 · Token 架构 — 3/10

**问题 A：没有分层。**
健康的 token 体系应是三层：

```
primitive（原始色板）  →  semantic（语义角色）  →  component（组件槽位）
  --blue-500: #06b6d4      --color-accent         --btn-primary-bg
                           --color-text-muted     --card-bg
```

当前 `tokens.css` 把三层**压成了一层**：`--accent` 既是原始色又是语义色又是组件色。后果是——想改"主按钮的蓝"但不影响"链接的蓝"，做不到。

**问题 B：主题间靠复制而非覆盖。**
`theme-emerald` / `theme-charcoal` / `theme-indigo` 三套，各自重新声明了约 40 个变量，其中 `--st-*-bg` / `--st-*-border` 六行**逐字重复、仅色相不同**（`tokens.css:222-227`、`265-270`、`308-313`）。

新增一套主题的成本 = 抄 40 行 + 改 3 个文件。**抄，就会漏。**

**问题 C：主题层不对称。**
默认主题写在裸 `:root` 上（`tokens.css:60`），其余三套用 `.theme-*` class。这意味着：
- `:root` 同时承担"共享基础变量"和"默认主题调色板"两个职责
- 想做浅色主题时，无法简单地"只用 class 覆盖"，必须动 `:root`

### 维度 3 · 主题切换机制 — 4/10

**问题 A：切换对 6/9 页面无效（最严重）。**

流程是这样的：
```
父页 switchTheme()  →  html.className = 'theme-emerald'
       ↓
postMessage → iframe → 子页 html.className = 'theme-emerald'
       ↓
子页 CSS 需要存在 .theme-emerald { ... } 规则才能生效
       ↓
但 B/C 方言的变量定义在裸 :root 上，没有任何 .theme-* 覆盖规则
       ↓
结果：变量值不变 → 页面纹丝不动
```

**问题 B：`className` 全量覆盖。**
`app.js:214`：`document.documentElement.className = theme;`
`workbench.html:395`：同样写法。

这行代码会**清空 `<html>` 上所有其他 class**。而 `app.js:55` 的 `postTheme()` 反过来又用 `document.documentElement.className` 当主题 key 读取。
一旦将来有任何需求往 `<html>` 上加第二个 class（比如 `no-js`、`wb-loading`），主题系统会**双向崩溃**：写的时候清掉别人，读的时候拿到脏值。

**问题 C：FOUC（主题闪跳）。**
`index.html:2` 的 `<html>` 上没有任何初始 class，`app.js` 在 `</body>` 前加载（第 40 行）。

非默认主题下按 F5 的真实时序：
1. 浏览器按 `:root` 的深蓝值渲染首屏
2. `app.js` 执行，读 localStorage，切到翡翠
3. `styles.css:16` 有 `transition: background 0.3s, color 0.3s`
4. → 用户看到一次 **300ms 的渐变闪跳**

修复成本极低（head 里加一段 3 行的内联脚本），但收益立竿见影。

**问题 D：无系统偏好跟随。**
4 套主题全是深色，没有 `prefers-color-scheme` 适配，也没有浅色主题。而 P5 已定要出"晴昼"浅色主题，当前的裸 `:root` 结构会让这件事变得别扭。

### 维度 5 · 语义色与无障碍 — 5/10

实测 21 组关键前景/背景组合（WCAG 2.1 相对亮度算法）：

| 方言 | 组合 | 对比度 | 判定 |
|------|------|--------|------|
| A | `--fg-default` / `--bg-page` | 14.71:1 | PASS |
| A | `--fg-muted` / `--bg-surface` | 6.38:1 | PASS |
| A | **`--fg-dim` / `--bg-surface`** | **3.44:1** | **FAIL** |
| A | `--fg-dim` / `--bg-input`（表头、hint） | 3.65:1 | WARN |
| B | **`--tx-4` / `--bg-2`** | **2.36:1** | **FAIL** |
| B | `--tx-3` / `--bg-1` | 4.15:1 | WARN |
| C | **`--faint` / `--panel`** | **3.04:1** | **FAIL** |
| C | `--faint` / `--canvas-2` | 3.17:1 | FAIL |

**合计：4 组 FAIL、2 组 WARN（未达 AA 4.5:1）。**

两个层面的问题：

1. **绝对不达标**：`--fg-dim`（A）、`--tx-4`（B）、`--faint`（C）都是"弱化文字"层级，承载表头、副标题、提示文案。3.0:1 左右在小字号（12-13px）下，长时间阅读明显吃力。

2. **相对不一致**：同一个语义层级（"弱化文字"），三套方言给出的是 3.44 / 4.15 / 3.04 三个不同亮度。**同一个角色在三个页面里深浅不一**——这是比绝对不达标更隐蔽的一致性缺陷。

**另有铁律未被遵守：**
`tokens.css:345-349` 的 `.badge.inconclusive` 复用 `--st-warn-*` 琥珀色，仅靠 `opacity: 0.85` 与 `.badge.run` 区分。
而 REQS-0011 §4.6 已立铁律：**inconclusive 必须是独立紫色相**（`#A371F7` / `#7c3aed`），不得复用 warn 琥珀。
该缺陷已被 **4 处生产代码引用**（`workbench.html:245 / 277 / 347 / 370`），属于"决策已定、代码未动"的断点。

### 维度 7 · 工程约束与可维护性 — 4/10

**主题注册分散在三处，需手工同步：**

| 位置 | 内容 |
|------|------|
| `tokens.css` | 4 个 `.theme-*` 选择器，各 ~40 行变量 |
| `app.js:205-210` | `THEMES` 对象，4 项（class → 中文名） |
| `index.html:22-25` | 4 个 `.theme-dot` 按钮（含 emoji 与 title） |

**加一套主题 = 改 3 个文件 + 抄 40 行变量。** 漏改任何一处，主题就是坏的（且不一定报错）。

**主题同步是 N×1 的分布式耦合：**
每个子页面都必须自己实现 `window.addEventListener("message", ...)` 监听（`workbench.html:403` 是唯一一处实现）。
9 个页面 = 9 处实现，漏一个就不同步，且**没有任何机制能发现"漏了"**。

**零构建约束下的既有包袱：**
- `styles.css:3` 用 `@import url("tokens.css")` —— `@import` 是串行请求，阻塞渲染
- 主题切换依赖 `postMessage` 跨 iframe 传播 —— 依赖 JS，JS 失败则主题失效，无 CSS-only 兜底

## 4. 根因归纳

把七个维度串起来，因果链是这样的：

```
组件层没接入（维度4，根因）
      ↓
页面各自复制设计稿的 token（维度1）
      ↓
形成 3 套互不兼容的方言
      ↓
主题切换只能作用于外壳（维度3）
      ↓
「4 套主题」名不副实，实际只有外壳会变
      ↓
外壳与内容区割裂 → 用户看到「丑」

同时：
无分层 + 靠复制（维度2）
      ↓
改一点要动一片，且必漏
      ↓
用户感受到「写得死」
```

**「丑」和「死」不是两个问题，是同一个根因的两个切面。**

## 5. 改造优先级（结论）

基于"投入产出比"排序，而非"问题严重度"排序：

| 优先级 | 动作 | 投入 | 收益 | 风险 |
|--------|------|------|------|------|
| **P0** | 消灭双层渐变 + 补 `color-scheme`（每个页面 2 行） | ~1h | 立竿见影，最大的视觉改善 | 极低 |
| **P0** | inconclusive 独立紫色相（1 个 token + 1 条规则） | ~15min | 兑现已立铁律 | 极低 |
| **P0** | FOUC 修复（head 内联 3 行脚本） | ~15min | 消除刷新闪跳 | 极低 |
| **P1** | 建三层分层（primitive / semantic / component） | ~4h | 架构地基 | 中 |
| **P1** | 修正 `--fg-dim` / `--tx-4` / `--faint` 对比度 | ~1h | 无障碍达标 | 低 |
| **P2** | 6 个页面接入公共 token（**按方言分批**） | ~2-3 天 | 让主题真正生效 | **高** |
| **P2** | 主题注册单一数据源（JS 驱动生成 CSS 变量） | ~4h | 加主题从"改 3 处"变"加 1 条" | 中 |
| **P3** | 收敛为 2 套（墨夜 / 晴昼）+ 出浅色主题 | ~2 天 | 兑现 P5 决策 | 中 |

**关键判断：P0 三项合计约 1.5 小时，能解决用户能直接感知到的 60% 的"丑"。**
架构重构（P1/P2）重要但不紧急，且必须在 P0 之后再动——否则会在错误的基线上大规模返工。

## 6. 复现与验证手法（可复用）

```bash
# 1. 找全所有 token 方言定义点
grep -rn "^\s*:root\s*{" apps/workbench/static/

# 2. 检查哪些页面接入了公共 token
grep -rln "tokens.css" apps/workbench/static/

# 3. 对比度实测
cd _tmp_theme_audit && python contrast.py

# 4. 验证主题是否真对某页生效（手工）
#    切到非默认主题 → 进入该页 → 若配色无变化，即未接入
```

**主题覆盖率的自动化检查建议：**
对每个页面断言「切换 `html.className` 后，`getComputedStyle(document.body).backgroundColor` 发生变化」。
这个断言可以做成冒烟测试，防止新页面重蹈覆辙。
