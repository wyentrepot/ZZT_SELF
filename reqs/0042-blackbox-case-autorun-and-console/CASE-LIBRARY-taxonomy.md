## 2. 排序规则建议

### 2.1 默认列表排序（控制台下拉「排序」默认项）

```
usage_rank(升) → domain → scene → region → name(字节序)
```

- `usage_rank`：`smoke`=0，`daily`=1，`acceptance`=2，`probe`=3，`forbidden`=9（默认折叠/置底，不隐藏，见 §4.2）
- `domain`：`cco` → `sta` → `ecu` → `bench`（与库的目录顺序一致：`用例库/00_总览.md:29-41` 先 STA 后 CCO；此处按我们控制台的主线倒过来，因为 0042 的主线是 CCO 侧抄表）
- `scene`：按 §1.3 表内顺序（组网 → 抄表 → 搜表 → 档案 → 路由 → …），**即「越靠近端到端主线越靠前」**
- `region`：`sgcc` 置顶，其余按省名拼音
- `name`：稳定字节序，保证「同一份数据两次渲染顺序一致」

**为什么把 usage 放第一**：`usage` 是我们唯一能表达「常用」的维度，而库里没有任何可直接聚合的常用度字段（§1.0）。放第一才能让「零参与跑一轮」看到的就是常用项。

### 2.2 「常用」的判定依据

**库中无「常用」口径，`grep -rn "常用" 用例库/` 零命中** → 按我方定义，三级判定（命中即停）：

| 级别 | 判定 | 依据 |
| --- | --- | --- |
| **P1 必测/核心** | 该场景命中 `业务层/37` §四「互操作性测试（11项，**必测**，核心业务）」之一 | `业务层/37_双模测试用例_业务.md:64`；11 项 = 全网组网 / 站点入网 / 站点离线 / 代理变更 / 全网抄表 / 广播校时 / 搜表 / 事件主动上报 / 实时费控 / 高频采集 / 多网络综合（`:67-77`） |
| **P2 判据够硬** | 判据落在 156 §四第 2/3 档：①「与实际一致/与设置一致」带回显对账 ②业务闭环（步骤 ≥ 8 且带异常分支） | `用例库/CCO/能力域/156…md:122-123` |
| **P3 我方主线依赖** | 出现在当前两个方案 `meter_smoke_min` / `smoke_meter` 的用例链里 | 我方 `REQS.md:536`「`meter_smoke_min` = `["bench_ready","meter_daily"]`；`smoke_meter` = `["bench_ready","meter_first_join"]`」 |

**明确排除的伪口径**（别误当「常用」）：
- Teambition 的 P0~P5 等级字段：100% 空（§1.0 实测）。
- 用例库总览 §七 的 P0~P3：是「该蒸馏哪张**卡**」的优先级，`用例库/CCO/00_CCO用例库总览.md:73`「`grep` 全库（排除用例库）确认的空白」，与跑用例无关。
- 156 卡里的「冒烟」：是**贬义判据评价**，说这些例「只能当冒烟，不能当协议一致性」（`:128`）。若控制台直接把 63 例 AFN 标成 `smoke` 会被误读为「推荐先跑」——建议 `smoke` 只用于**我方自建的最小链**，AFN 单帧例标 `acceptance(judge=weak)` 并在 UI 上显示判据档位。
