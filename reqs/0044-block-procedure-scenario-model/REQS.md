## 1. 背景

### 1.1 用户提出的困惑（原话）

> 「当前用例库与场景测试流程好像冲突了？我理想状态是用例库是零碎的步骤验证，组合起来就是黑盒测试。场景测试就是专门针对开发过程中特定方案验证的测试，但是我看现在场景测试好像被用例库给冲突掉了？」
> 「我一直想要一个编排的功能，每个场景测试，本质就是多个测试用例块组成的，无非是组网，抄表，之后再加上一些不常用块的组合。」

### 1.3 用户对"解耦"的关切（本次需求的核心问题之一）

> 「是否测试用例与整体项目是解耦的？」

当前实况（分三层，结论不同）：

| 层 | 当前解耦度 | 证据 |
|---|---|---|
| 契约层（块协议、能力适配） | **已解耦** | `libs/` 不 import `apps/`（分层铁律）；块只通过 `capabilities/*` 访问能力面 |
| 资产层（块声明、用例、场景） | **强耦合**：默认表地址、协议、期望数值、省份规则、串口映射全部硬在声明里 | `data/case_defaults.json`；`data/cases/*.json` 里写死 `1234.56` / `220.1` |
| 执行层（跑起来） | **必然耦合**：依赖工作台 HTTP + 串口 + 台架 | `capabilities/simcon.py` 走 `/api/simcon/*` |

**结论**：不能笼统说"解耦/不解耦"，必须区分**能读**（阅读、审查、校验）与**能跑**（上真机）。本需求要立的就是这条边界（§5）。

## 2. 目标

1. **判据归位**：块只返回**观测**（看到了什么 / 没看到什么 + 原因），不输出通过/失败；通过与不通过由**调用方（Procedure 层）**按"期望 vs 观测"判定。
2. **实体归一**：用例与场景是**同一个实体（Procedure）**的两种生命周期，不再是两套系统；术语按标准正名（Block → Procedure → Suite → Run）。
3. **块可组合**：块声明补 `kind`（真测试 / 台架准备 / 收尾 / 探测）、`side_effect`（无 / 可逆 / 不可逆）、`version`；补齐事实链，让顺序由事实约束而不是靠人记。
4. **编排层有判据**：Procedure 层补齐场景级判据（只做一次 / 先后关系 / 两处一致），并规定"无判据不得入库"。
5. **解耦边界成立**：块与 Procedure 的一切声明，脱离台架也能**离线校验**；跑起来才需要台架。
6. **文档与声明同源**：`docs/blocks/*.md` 由块声明生成（只读），不允许手写漂移；每份块文档必须有"反例"节。

## 4. 模型设计（本需求的主体）

### 4.1 四层与术语正名

```
Run（一次执行）
  └─ Suite（方案/批次：这次跑哪些 Procedure）        ← 回归批次，stop_on_fail
       └─ Procedure（编排层：有顺序、有前置、有判据）  ← 用例与场景都是它
            └─ Step（步骤：引用一个块 + 该步的期望 + 失败策略）
                 └─ Block（原子块：一次交互的观测单元）
```

| 术语 | 标准对应 | 本仓库现状 | 本需求 |
|---|---|---|---|
| Block | low-level test case | 叫 Block ✅ | 保持，**只观测不判定** |
| Procedure | test procedure | 叫 Case ❌ | **正名 Procedure**，用例与场景统一 |
| Suite | test suite | 叫 Suite ✅ | 保持 |
| 场景 | 行业口语（非标准实体） | 独立一套 `scenarios/*.json` ❌ | **降为 `Procedure.kind=scenario`**，不新增实体 |

### 4.2 判据归属（本需求最重要的一条）

**旧**：`Block.assert` 判"值对不对" → 块直接出 pass/fail。
**新**：拆成三件，各归各位：

| 层 | 拥有什么 | 不拥有什么 |
|---|---|---|
| Block | 观测（帧/读数/是否取到/完整性/没拿到时的原因）+ 该交互的**口径说明** | 不判"值符不符合期望" |
| Step（Procedure 里的一步） | **期望**（引用哪块 + 期望观测长什么样 + 失败策略 + 等待预算） | 不写帧、不算参数 |
| Procedure | 跨步判据（只做一次 / 先后关系 / 两处一致）+ 结论聚合 | 不重复单步的期望 |

**执行链保持不变**：Block 返回观测 → 求值器按 Step 的期望产出步骤态（`pass/fail/skipped/unknown`）→ Procedure 聚合四态。**四态语义一个字不改**，改的只是"谁在判"。

**为什么必须这么改**（用户原话的落地）：同一份观测在建档用例里期望"含该地址"，在清库用例里期望"不含"。判据写在块里，块就只能服务一种期望，另一种要另造块 —— 块失去复用性，判据随用例漂移。

### 4.3 块元数据（新增三个字段）

| 字段 | 取值 | 为什么必须 |
|---|---|---|
| `kind` | `case`（真测试）/ `setup`（台架准备）/ `teardown`（收尾）/ `probe`（探测） | 台架准备判 pass 会混进产品通过率，造"永真用例"（D-6） |
| `side_effect` | `none` / `reversible` / `irreversible` | 复位、烧录不可逆，只能标顺序敏感；开表口、改档案可逆，必须有收场动作（D-7） |
| `version` | 整数 + 声明内容指纹 | 判据/默认值一改，历史结果不可复现；必须能回答"当时用的是哪一版" |

### 4.4 场景 = Procedure 的第二种生命周期

**不新建实体**，只在 Procedure 上加一个字段区分：

| `kind` | 语义 | 生命周期 | 证据落点 | 是否进回归方案 |
|---|---|---|---|---|
| `regression` | 常驻回归（如单表抄表） | 长期，随台架演进 | `data/case_runs/<run_id>/`，保留近 30 轮 | 可进 |
| `scenario` | 一次性方案验证（如 698 分帧专项） | 跟某个需求走，验证完归档 | `evidence/<req_id>/<run_id>/`，长期留存 | **不进** |

**单向沉淀**：场景验证通过后，把稳定部分提炼成回归 Procedure，场景文件标 `promoted_to: <procedure_id>` 后归档。**禁止反向**（回归用例不因某个场景而改判据）。

### 4.5 场景级判据（编排层唯一被允许新增的判据）

| 类型 | 表达 | 例子 |
|---|---|---|
| `only_once` | 某块在一次运行中最多执行 N 次 | 整轮只允许复位一次 |
| `cross_step` | 步骤之间的蕴含关系 | s3 有观测 ⇒ s2 必然有观测 |
| `flow` | 事件时序比对（复用 `orchestration/compare.py` 的五类差异：命中 / 缺失 / 超时 / 乱序 / 负向命中） | 先扫描后入网；某帧不该出现 |

### 4.6 块文档规范（已用五份文档验证）

- 一份块一份 md，命名 `case-<中文动作>-<块id>.md`；
- **纯说明、禁代码**，用 ASCII 图画出执行路径，**每个判定点必须三个去向**（符合 / 不符合 / 没拿到）；
- 必备节：职责、执行路径、返回什么、调用方怎么判、参数、副作用、**反例**、不做什么、**调用方义务**、与当前实现的差异、被引用（自动生成）、待确认；
- md 由声明**生成**（只读），禁止手写：手写的说明必然与实现漂移（D-5 已是现成例子）。

## 5. 解耦边界（回答"测试用例与整体项目是否解耦"）

### 5.1 立规矩

| 能力 | 要求 | 判定方式 |
|---|---|---|
| **读**（列出、展示、审查文档） | **离线可用**：不启动工作台、不接台架 | 断网、不启服务，`list` / `show` / 文档生成全部可用 |
| **校验**（声明合法性、事实链、文档与声明一致） | **离线可用** | 不需要串口与服务即可跑 `check` |
| **跑**（执行） | **允许依赖台架**，但只能通过能力适配层访问，块内不得出现地址/端口/URL | 代码扫描：块层零 HTTP 字面量、零端口常量 |

### 5.2 资产层与本项目的分离

| 内容 | 归属 | 规则 |
|---|---|---|
| 块协议（需要什么事实/提供什么事实/副作用/判据口径） | **框架**（跨项目复用） | 不含任何项目默认值 |
| 台架默认值（表地址、协议、串口映射、端地址） | **项目配置** | 只允许出现在配置里，不允许出现在块声明与 Procedure 里 |
| 期望值与用例内容（1234.56 kWh、98%） | **项目资产** | 允许出现在 Procedure 的期望里；必须标注适用范围（台架/协议/省份） |
| 固件实现细节假设 | **禁止** | 只依赖协议与可观测行为，不依赖实现内部 |

### 5.3 验收口径

一句话：**框架可以离开项目被读懂、被校验、被评审；项目资产离开台架可以准备好，但必须接台架才能出结论。**

## 6. 迁移与风险

### 6.1 迁移对象

| 对象 | 现状 | 迁移动作 |
|---|---|---|
| 16 个块 | 全部内建判据 | 拆成"观测 + 口径说明"，判据搬到 Step 期望；补 `kind` / `side_effect` / `version` |
| 7 条用例 | 无编排层判据 | 补 `expects`；改名为 Procedure；`kind=regression` |
| 2 个方案 | 只有 `case_ids` | 保持，指向 Procedure |
| 6 个场景模板 | 独立一套，只读 | 翻译成 `kind=scenario` 的 Procedure，删除旧路径（或降为只读适配器） |
| 仓库外 `autotest/`（22 用例 + chains） | 命令式，只有 bool 结论 | 降为薄适配器（生成 plan 调 CLI），不保留第二套判定 |
| `orchestration` 监控/比对 | 独立一套 | 只保留 `flow` 判据的数据来源，页面并入 Procedure |

### 6.2 顺序（不允许跳）

1. 先立契约与文档（本需求 REQS + 五份块文档）；
2. 再补"观测 / 期望"求值器（改执行器，四态不变）；
3. 再迁移块（先迁单表抄表链的 4 块 + 查档块）；
4. 再迁移用例与场景；
5. 最后收编旧路径（`autotest/`、`scenarios/` 只读页）。

### 6.3 已识别的具体缺陷（迁移时必须一并修）

| # | 缺陷 | 影响 |
|---|---|---|
| R-1 | 组网的主节点数**只在本页统计**（默认 32 条），总数超一页且主节点不在首页时读成 0 | 分子虚高 1，把"差一个"判成达标 —— 假 PASS 类事故 |
| R-2 | 块声明里的断言**没有求值器** | 声明与实现脱节，文档/声明不可信 |
| R-3 | 等待预算三处不一致（声明、用例、模块头注释） | 结论不可比；注释误导读码人 |
| R-4 | 期望值钉死（`1234.56` / `220.1`），真表会漂 | 日常回归假失败 |
| R-5 | 整轮超时**不杀线程**，僵尸线程继续占串口 | 下一轮可能互相踩 |
| R-6 | `cleanup` 是死字段（0/16 声明，执行器注入但无人执行） | 连跑两次结论可能不一致 |
| R-7 | 场景里的人肉注入 | 违反零介入红线 |

### 6.4 风险

| 风险 | 应对 |
|---|---|
| 判据搬走后"回了确认但没落地"漏判 | **调用方义务**：以建档成功为目的的 Procedure，必须显式接查档步并声明期望；缺判据不许入库（硬门禁） |
| 迁移期两套口径并存 | 迁移期以代码为准，文档标"目标态"；每个块迁移完成即换标记 |
| 块越迁越厚（把期望也塞回块里） | 代码门禁：块层出现"期望值"字样即失败 |

### 6.5 不采用现成框架的理由（已评估）

| 候选 | 结论 |
|---|---|
| Robot Framework / pytest / BDD | 不采用。四态（尤其"说不清"）、单步预算式等待、只收不发/等存数都表达不了；迁移估值 30–40 人日，换来的主要是报告样式 |
| 直接复用模拟集中器的步骤机当编排层 | 不采用。它没有事实层、没有四态、没有 Procedure 层级；只**吸收**它的步骤语义作为块的执行协议 |
| 现成可视化编排平台（如 MeterSphere 等） | 不采用。步骤=HTTP 请求，四态要塞进脚本断言，判据全部沉到脚本里；可借鉴其 UI，不接其引擎 |

### 6.6 编排界面（后置）

不在本需求范围。先立契约（本需求），界面留到契约稳定后：清单式（块库 + 排序 + 按块自动生成参数表单），**不做流程图拖拽**。

## 7. 验收标准（可检查）

| # | 验收项 | 判定方式 |
|---|---|---|
| AC-1 | 块返回**不含**通过/失败结论 | 代码扫描：块层无结论常量、无"通过/失败"字样 |

| AC-10 | 单表抄表链迁移完成 | 5 个块（含查档）+ 1 条流程在真机出结论，且旧判据路径已删除 |

3. **等待预算**：写死在 Procedure 里，还是允许块默认（默认一改，历史结论不可比）？
4. **期望值容差**：真表电压会漂，是否给容差（如 ±0.5 V），还是只对模拟表用固定值？
5. **解耦边界**是否认可 §5 的三档（读/校验离线、跑依赖台架）？
6. **`autotest/` 与 `scenarios/` 旧路径**：直接删除，还是保留为只读适配器（更稳但多一处维护）？

### 8.1 v2 结论（2026-11-24 用户拍板，六条全部已定）

| # | 问题 | 结论 | 影响 |
|---|---|---|---|
| 1 | 查档步 | **要**。单表抄表流程固定 **6 步（日常）/ 7 步（首次）**，①b 查档为必备步 | 流程文档已按此写；`archive.query` 块文档列入第二批 |
| 2 | 组网节点数超一页 | **必须支持翻页拉全**。一次查询条数不足时按总数翻页，主节点数取全才叫观测完整；取不全必须标"观测不完整"，不许静默按本页数 | 取代 R-1 的"只标注不完整"方案；组网块要改翻页逻辑 + 门槛用取全后的真实数 |
| 3 | 等待预算 | **写死在 Procedure 里**，块默认值只作兜底；缺等待预算的等待型步骤（组网/绑表/抄表）视为缺判据 | 校验加一条硬门禁；块文档参数节改为"用例必须显式给" |
| 4 | 期望值 | **只要求"有值且可解"，不校验数值真实性**（不比对 1234.56 kWh / 220.1 V）。数据正确性不在本框架的验证范围 | 抄表块默认不比具体值；显式给期望值时才比对。流程④⑤判据改写；容差问题随之消失 |
| 5 | 解耦三档 | **认可**（读/校验离线，跑依赖台架） | §5 生效 |
| 6 | 旧路径 | `autotest/` 与 `scenarios/` **直接合并成一个**（统一并入 Procedure），不保留两套执行/编排路径 | §6.1 迁移项改为"合并"；P5 收口动作明确为"删两套、留一套" |

**第 4 条的边界（避免执行者误解）**：不比对数值，但**仍然必须**验 CS 合法、控制码正常、DI 回显、数值可解。即"证明这一次真的读到了表里的一项合法数据"，不证明"这个数是对的"。

## 变更 3 ｜ 2026-11-24 ｜ 领导三条补充决策（L1 / L2 / L3）

- **改成什么**：
  - **L1（补充 §4.4）Procedure 增 `kind: regression | scenario | setup`**：
    `setup` = **台架准备型流程**（如 `bench_ready`）。它不是被测对象的测试，而是把台架
    备到可测状态（会话在位、开表口）。报表中 setup 行的大类/子类显示「—」（字段为 null），
    且**不计入产品通过率**（分母不含 setup 行）。与块级 `kind=setup` 的区别：块级 setup
    是单个原子动作，Procedure 级 setup 是**流程**编排（编排的就是这些 setup 块）。
  - **L2（新增 §9.1）报表契约字段冻结（前端 Demo 代理按同一份开发）**：作为运行结果
    **新字段**（`result.json` 与 `GET /api/cases/runs/{run_id}` 读模型），语义只加不改：
    ```json
    run.report.rows[] = {
      "group": "测试大类（取 category.scene；kind=setup 时为 null，渲染为 —）",
      "subgroup": "测试子类（取 category.domain；kind=setup 时为 null）",
      "name": "用例名称（Procedure 标题）",
      "kind": "setup|regression|scenario",
      "steps_text": "1.xxx；2.xxx（业务动作文本，零块名，0042 D11-2）",
      "verdict": "pass|fail|blocked|inconclusive",
      "reason": "一句话人话原因（pass 为 null；如「组网超时：等待90s仍处学习态」「台架不具备：串口桥未运行」）",
      "evidence_paths": ["result.json 等证据路径"],
      "counts_as_product": "setup=false，其余 true"
    }
    run.report.summary = {"total":n, "pass":n, "fail":n, "blocked":n, "inconclusive":n,
                          "product_pass_rate":"x/y（分母不含 setup 行）"}
    ```
  - **L3（补充 D11-1）失败原因 = 一句话人话口径**：每行 `reason` 必须是一句可读的
    人话（结构：「<动作/环节>：<具体原因>」），禁块名、禁帧 hex、禁堆栈；pass 行 reason
    为 null。人话模板沿用 `core/report.py` 的四类口径（超时 / 不符 / 台架不具备 / 说不清），
    该模块仍是 CLI / API / UI 共用的唯一一份人话实现。
- **为什么**：领导 2026-11-24 三条补充——①台架准备型流程不得混进产品通过率（与 §4.3
  块级 kind 的动机同源，落到流程层）；②报表契约要冻结，前端 Demo 代理按同一份字段开发，
  避免后端先行后字段漂移；③失败原因必须是用户能直接读懂的一句话（与 0042 D11-1 一脉相承，
  收紧到「每行一句」）。
- **影响**：`core/models.py`（ProcedureSpec.kind / category / protocols）、
  `core/report.py`（rows/summary 组装，复用 classify_failure / action_label）、
  `apps/workbench/cases_api.py`（RunRecordView.report 新字段，落盘与读回一致）、
  `data/cases/bench_ready.json`（kind=setup）。四态语义、聚合优先级、执行链**均不改**。
- **变更前基线**：v2（本文 §8.1）
- **变更后基线**：v3（本文）
- **被取代**：无（L1 是 §4.4 的扩展，L2/L3 是新增契约；冲突点以本条为准）

## 变更 4 ｜ 2026-11-24 ｜ 生产页移植期契约口径对齐（kind 徽标 / 历史运行索引 / 信息性事实中性显示）

- **改成什么**：
  - **L2 口径修正（setup 行 `steps_text`）**：推翻变更 3 中「setup 行 `steps_text` 一并置
    null」的约定——setup 行的 `steps_text` **允许带真实步骤文本**（`1.xxx；2.xxx`，
    口径同 regression 行：业务动作文本、零块名，0042 D11-2）。页面按「**有值就渲染**」
    处理：null/空 → 「—」，有值 → 原样渲染。`group` / `subgroup` 为 null（渲染「—」）
    的约定**不变**。
  - **L2 口径澄清（`evidence_paths`）**：`evidence_paths` 为**宿主机绝对路径**（`result.json`
    / 运行目录 / 日志的真实落盘位置）。页面只提供**复制**（点击路径或「复制」按钮即复制到
    剪贴板），不做打开 / 下载跳转。
  - **新增端点（§9.1）`GET /api/cases/runs?limit=N`**：历史运行索引，返回最近 N 轮
    `{run_id, verdict, finished_at, case_names, summary}`（`summary` 含 `headline` 与
    `product_pass_rate`），**新的在前**。`limit` 缺省 10、上限 50（超界夹取，不回 422）；
    读各 run 目录 `result.json` 的头部字段，缺文件 / 坏文件的轮次**跳过并忽略**；
    选中某轮后的完整读回仍走既有 `GET /api/cases/runs/{run_id}`（同一条载入路径）。
  - **页面小修（UI 口径，非新契约）**：①用例卡片显示 kind 徽标（回归=默认色 / 场景=蓝 /
    台架准备=灰；消费 `GET /api/cases` 读模型新增的 `kind` 字段——字段只加不改）；
    ②清单页加「历史运行」小下拉（消费 runs 索引端点，选中即载入结果视图）；
    ③台架横幅中**非闸门事实**（`required=false` 的运行期回写型，如 `archive.written` /
    `nwk.joined` / `sta.addr_obtained` 等）三态芯片用**中性灰**，不再用黄色「未知」，
    避免误读为台架故障。**闸门判定逻辑一字不动**（`ready` / `unmet_required` 置灰运行钮
    的口径不变）。
- **为什么**：生产页（`apps/workbench/static/pages/cases/`）按 `docs/ui/cases_v2_demo.html`
  移植联调时发现四处缺口——①setup 行步骤文本被按 null 处理会让「台架准备了什么」不可读；
  ②证据路径不是宿主机绝对路径时「复制后找不到」；③历史运行只能手输 run_id，缺一个就近的
  轮次入口；④回写型事实独立探测恒 unknown，黄色「未知」在横幅上像故障。均为显示层与
  索引层补齐，不改四态语义、不改聚合优先级、不改闸门判定。
- **影响**：`apps/workbench/cases_api.py`（`CaseView.kind`、`GET /api/cases/runs` 索引端点）、
  `apps/workbench/static/pages/cases/{cases.html,cases.js}`（kind 徽标 / 历史运行下拉 /
  信息性事实中性灰芯片）、`apps/workbench/test_cases_api.py`（新端点与新字段测试）。
  `libs/` 执行逻辑、四态语义、闸门判定**均不改**。
- **变更前基线**：v3（本文含变更 3）
- **变更后基线**：v4（本文）
- **被取代**：变更 3 中与「setup 行 steps_text=null」相关的表述以本条为准（页面按有值即渲染）；
  其余 L1/L2/L3 约定继续生效。
