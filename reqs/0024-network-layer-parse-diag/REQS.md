## 1. 背景与问题

当前项目对**网络层（NWK）/MAC 链路层**的解析与 CCO 交互观测基本空白，而原料其实已在手：

1. **侦听台封装帧已含空口原料**：GW 侦听台封装帧 `7E FF 02 <20字节头> <FCH16> <MPDU> ... 7E`（见 `apps/listener/network_assessment.py` 模块注释），FCH + MPDU 完整可达——`network_assessment.py` 已能从中裸字节抠出 NID / 中央信标 / CCO MAC / 信标周期计数，证明硬件透传可行。
2. **解析库停在 4-3 应用层**：`libs/parser_lib/adapters/adapter_dualmode/` 只解析 4-3 报文 ID 级（`__init__.py` 明确写「MAC 地址属于 4-2 数据链路层信封（本期后置）」）；NWK 管理帧（关联/代理变更/心跳/路由修复/冲突上报）**零解析**。
3. **网络评估靠文本硬抠**：`network_assessment.py` 的 A 档靠裸字节识别"是信标但不解内容"；B/C 档（CSMA 占用、路由剩余时间、信道变更次数）从 GwHPLCAnalysis.dll 的 Detail **文本**正则提取，脆弱且丢信息。
4. **蒸馏知识无落点**：蒸馏库 07/08/11 三篇已把工程门限（退避 40/60/600s、心跳 4 周期离网、冲突仲裁 307ms/20.7s/30min 等）和状态机讲透，但项目里没有对应的结构化消费方。

本需求是后续"诊断流程 / 自动化检测 / AI 直诊"各功能的**解析地基**（功能点总表 A1-A3，见 2026-09-05 会话产出）。

## 2. 目标（G1-G3）

| # | 目标 | 内容 |
|---|------|------|
| G1 | 4-2 链路层信封解析 | 解 FCH / 表4 MAC 头（TEIs/TEId/MSDU 序号/重启次数/路由总·剩余跳数/MACaddrFlag 头长 16·28）/表13 帧控制（定界符 0-3、NID、FCCS）/表19·30 帧长域/表23·34 选择确认（PB 位图/LQI/staLoad）；补上 adapter_dualmode "后置"的 MAC 层 |
| G2 | NWK 管理帧解析 → 组网事件流 | 解 table60/70（关联 req/cnf，含 9 种拒绝原因码 + 退避时间）、table79/84/88（代理变更）、table94（心跳位图）、table91（离网指示）、table111/114/117/118（路由修复三步曲）、table102/121（NID/信道冲突上报）；输出事件级结构（事件类型/TEI/MAC/参数/方向/时间），落库供查询。注意：这些帧经 1376.2 AFN=05 透传，串口侧与空口侧都可能观测到，两条通路都要能出事件 |
| G3 | 信标条目级解析 + 时隙重建 | table38 头（信标类型/允许关联/NWKFormNo/CCO MAC/周期计数）+ 条目逐项解析（47 站点能力/48 路由参数/49 频段变更/50 时隙分配/54 无线路由/55 无线频道变更）+ BPCS CRC32 校验 + 信标/TDMA/CSMA/绑定CSMA 四时段起止重建（NTB 25MHz 换算）；`network_assessment.py` 换用该结构化解析替换裸字节逻辑，B/C 档改为从结构化字段取数 |

**范围外（后续需求候选，不在本需求承诺）**：A4 台区拓扑重建、A5 组网时序/STA 状态机视图、A6 通信流追踪空口侧扩展。

- **管理帧透传性未验证**：信标可见已证实，但 table60/70 等短管理帧是否被侦听台硬件完整透传**未核验**——列为 Step 0 前置，若空口侧抓不全，则 G2 事件流以 1376.2 串口侧（AFN=05 透传）为主通路。
