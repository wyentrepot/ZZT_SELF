## 1. 背景与问题

现状盘点（2026-09-17 实测）：

1. **解析能力已存在但没有"日常入口"**：`libs/parser_lib` 是纯 Python 解析库（零第三方依赖），
   适配器注册表 `build_adapters()` 已含 645 / 698.45 / 1376.2 / 双模4-3，
   `ProtocolRouter` 支持自动嗅探 + 手动指定；1376.2 有独立 dict→dict 入口
   `parser_lib.decode_13762`。脚本 `PYTHONPATH=libs` 直接 import 即可用，
   **不需要工作台 8790、不需要解析网关 8700、不需要 DLL**——但这件事没有被任何
   技能文档告诉 AI，AI 日常排查时默认只能想到起工作台走 8700/8790 链路。
2. **ai-control-plane 技能范围过重**：技能默认按"任务门面 v2 八步/全功能"组织
   （侦听台、串口、烧录、simcon、组网观测……），日常大多数场景只需要其中
   **应用层帧**一小部分：比如 1103 并发抄表——外层是 1376.2 协议，
   1376.2 应用载荷里再携带 698/645 帧。技能缺少一个"日常轻量档"：
   明确日常只启用应用层解析/构帧这一部分，其余全功能路径按需再启用。
3. **构帧能力分散且缺回验**：测试场景中 CCO 侧要构帧做测试用例（TDD）：
   先查知识库协议蒸馏卡拿到帧格式 → 测试代码产帧 → 需要对产出的帧做**验收**。
   现状：1376.2 适配器有 build 动作、simcon/scenario_codec 有下发构帧，
   但没有统一的"构帧 → 解析回验 → 验收结果 JSON"闭环接口；
   698/645 应用层构帧能力与入口也未统一暴露。

## 2. 用户诉求（原话归纳）

1. 修改技能范围：日常使用时只需要启用部分即可，比如应用层的解析——
   比如 1103 并发抄表之类，里面包裹的 1376.2 协议，然后 1376.2 协议里面携带 698/645 协议。
2. 测试场景：CCO 要构建帧做测试用例；有了知识库的协议帧格式之后要做 TDD 测试，
   需要有构帧的接口；测试代码产出帧后，要有验收帧的结果。
3. 日常只考虑应用层帧：1376.2 协议、698、645。要有**构建 + 解析**能力：
   输入原始帧，输出 JSON 解析结果给 AI。

## 3. 目标（当前生效基线 v1.2）

### 3.1 应用层帧解析接口（免工作台，脚本直接可用）

- 入口：统一 `decode` 门面（复用 `libs/parser_lib`，禁止复制解析逻辑）：
  输入原始帧（hex 字符串或 bytes），输出 JSON。
- 覆盖协议（仅应用层）：
  - **1376.2**：外层帧解析；内嵌的 698/645 帧递归解出（`nested`），
    典型样例 = 1103 并发抄表（1376.2 转发应用载荷内嵌 698/645）；
  - **698.45**：直连帧独立解析；
  - **645-2007**（645-1997 顺带兼容）：直连帧独立解析。
- 自动嗅探（ProtocolRouter）+ 手动指定协议两种模式，
  **两种模式的容错语义不同**（2026-09-17 实测定稿）：
  - **自动模式（不指定协议）= 严格**：各协议 confidence 打分，校验和（CS/FCS/HCS）
    参与打分；最高分低于阈值时输出「无法识别 + 各协议得分 + 建议 --protocol 重试」，
    **禁止兜底硬解**（现路由对全 0 分会兜底选"双模4-3"，必须改）。
  - **指定模式（--protocol）= 宽容，允许错误帧**：跳过 confidence 门槛强制
    `adapter.decode`，照常输出结构/字段/数据项，校验失败以 **warnings** 表达
    （实测：错 CS 的 645 → `CS校验失败: 帧内0x33 vs 计算0xD7`；
    残缺 698 → `FCS校验失败`+`数据不完整`，均不抛异常）。
    真正无法解的帧（适配器抛异常）由门面捕获输出错误 JSON，不得裸崩。
- 输出 JSON 面向 AI 消费：结构/字段/数据项/嵌套帧/warnings，口径与
  `parser_lib` 适配器现有输出一致（零分叉），必要处附知识库蒸馏卡出处。

### 3.2 应用层构帧接口（测试用例 / TDD 支撑）

- 入口：统一 `build` 门面：输入语义参数（协议 + AFN/Fn 或 DI/OAD + 参数 +
  方向等），输出帧 hex + 长度 + 校验说明。
- 构帧依据：**知识库协议蒸馏卡为权威口径**（协议层帧格式卡）；
  1376.2 复用既有 build 能力；645/698 构帧按常用集实现
  （读类/设置类典型帧，P0 盘点后定清单）。
- 不碰串口：纯构帧，真实下发仍走既有 simcon / module-actions 链路。

### 3.3 帧验收（回验）接口

- 入口：统一 `verify`（round-trip）门面：输入帧 hex（或构帧结果），
  自动用解析器回解，输出验收结果 JSON：
  `ok / 差异清单（字段级 diff）/ warnings /（可选）与原始意图参数的比对`。
- 用途：测试代码产帧后的**验收帧结果**；TDD 中作为帧级断言依据。

## 4. 边界

- **只管应用层帧**：1376.2 / 698.45 / 645-2007（1997 顺带）。
  GW 封装帧、双模 4-3、网络层/NWK 组网帧**不在日常档范围**
  （已有 REQS-0024/0026 链路，技能全功能档覆盖）。
- **纯帧工具**：不碰串口、不采集、不下发、不烧录；
  与 8700 net48 深度解析网关无依赖关系（口径对拍可作为验收手段之一）。
- **复用优先**：解析必须复用 `libs/parser_lib`；构帧尽量复用既有
  build/scenario_codec 能力，缺的部分补齐——禁止另起一套解析/构帧实现。
- 免工作台 ≠ 替代工作台：涉及真机、串口、取证时仍走全功能档。
- 双副本同步：技能改动必须同时落在工作区副本与全局技能库副本
  （§3.4.3），先调和后同步；两仓提交各自独立留痕。
