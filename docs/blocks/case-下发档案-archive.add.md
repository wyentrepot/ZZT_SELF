# `archive.add` — 下发从节点档案（只观测，不判定）

> 版本 **v0.2（待审）** ｜ 所属层：原子块 ｜ 领域：档案（CCO）
> 一句话：**把一只表的地址下发进 CCO 档案，如实返回"命令发出了没有、被接受了没有"；不判断档案该不该存在。**

---

## 0. 本版改了什么（相对 v0.1）

| 项 | v0.1（旧） | v0.2（本版） |
|---|---|---|
| 判定权 | 块自己判"含该地址 → 通过" | **块不判定**，只返回观测；通过/不通过由调用方（用例/场景）决定 |
| 块级结论 | 通过 / 失败 / 说不清 | 只有"拿到了 / 没拿到（原因）" |
| 回查档案表 | 块内自己做 | **移出本块**，由独立的查询块承担，由用例显式编排 |

**为什么改**：同一个"查档案"动作，在建档用例里期望"有"，在清库用例里期望"无"。判据写在块里，这个块就只能服务一种期望，另一种用例就得另造一个块——块失去复用性，判据也会漂移。

---

## 1. 一句话职责

**下发一只表的从节点档案，返回命令的执行观测。**

- 它回答：*"这条建档命令发出去了吗？CCO 接受了吗？"*
- 它**不**回答：*"档案里现在有没有这只表？"*（查询块的事）
- 它**不**回答：*"这次建档算不算通过？"*（调用方的事）

---

## 2. 做什么（执行路径）

```
调用方给出：电表表地址（645 口径，12 位，如 123456789012）
        │
        ▼
 ① 预查（只读）：这只表已经在档案里了吗？
        │
        ├─ 查询没拿到（串口忙 / 台架不通 / 无应答）
        │        └──→ 返回【未下发 · 原因：无法确认现状】
        │
        ├─ 已存在 ───────────→ 返回【未下发 · 原因：已存在】  一个建档帧都不发
        │
        └─ 明确不存在
                 │
                 ▼
 ② 下发建档（11H-F1）
    ※ 档案地址 = 电表地址整体反序（123456789012 → 129078563412）
                 │
                 ▼
 ③ 等确认（00H-F1，默认 5 秒）
                 │
        ├─ 收到确认 ──────→ 返回【已下发 · 确认已收到】
        └─ 没收到确认 ────→ 返回【已下发 · 确认未收到 · 原因】
```

**图上没有"通过 / 失败"** —— 因为这两件事不归块管。

**预查为什么在块内**：CCO 对重复建档会回否认帧。不预查就发，第二次跑同一用例会收到一个"看起来像失败"的否认帧——那是块自己造出来的噪音。预查是执行策略，不是判定。

**预查只用于"要不要发"，不回传档案内容**：档案内容由查询块提供，避免两个块都返回同一份数据、口径不一致。

---

## 3. 返回什么（观测三件套）

| 返回项 | 取值 | 说明 |
|---|---|---|
| **是否下发** | 已下发 / 未下发（已存在） / 未下发（无法确认现状） | 未下发必须给原因，不许沉默 |
| **确认是否收到** | 收到 00H-F1 / 未收到 | 未下发时此项无意义 |
| **没拿到时的原因** | 串口被占 / 台架不可达 / 等待超时 / 参数非法 | 只描述"为什么没拿到"，不描述"算不算失败" |

**没有"说不清"这个块级结论。** 块只有两种处境：拿到了观测，或者没拿到并说清为什么没拿到。至于"没拿到"意味着什么，是调用方结合自己的期望来判断的。

---

## 4. 调用方怎么判（三个典型用法）

### 用法一：验证"建档成功"

```
步骤1  archive.add    期望：已下发 + 确认收到
步骤2  archive.query  期望：档案表含 129078563412
结论：两步的观测都符合期望 → 通过
```

### 用法二：验证"清库成功"（你举的那个例子）

```
步骤1  archive.del    期望：已下发 + 确认收到
步骤2  archive.query  期望：档案表**不含**该地址
       ※ 若查出来还有 → 由用例判失败，不是由查询块判失败
```

### 用法三：验证"幂等"（同一用例连跑两次）

```
第一次：archive.add → 已下发 + 确认收到
第二次：archive.add → 未下发（已存在）   ← 正常观测，不是失败
        archive.query → 含该地址
结论：两次都通过
```

**同一个查询块，在用法一里期望"含"，在用法二里期望"不含"——这就是判据必须归调用方的原因。**

## 5. 参数

| 参数 | 含义 | 默认值 |
|---|---|---|
| 电表表地址 | 645 口径 12 位表地址，块内部换算成档案地址 | 配置默认（出厂 `123456789012`） |
| 通信协议 | 2 = 645 / 3 = 698 | 2 |
| 确认等待 | 等确认帧的秒数（等待型步骤的预算须由用例写死，块默认仅兜底，0044 §8.1-3） | 5 秒 |

三条纪律：

1. **一次只能给一只表**。给多个 → 报参数错，不猜先发哪个；
2. **给了但不合法 ≠ 没给**。非法地址报错，绝不静默换成默认表地址（否则会动到不该动的表）；
3. **地址换算只有一处**：电表口径 ↔ 档案口径整体反序，调用方不用管。

## 7. 反例（怎么证明它没撒谎）

判据搬走之后，块要证明的是**观测本身的正确性**：

| # | 反例 | 期望观测 | 防的是 |
|---|---|---|---|
| R1 | 表已在档案里 | 返回"未下发（已存在）"，**零建档帧** | 重复下发造出否认帧噪音 |
| R2 | 串口被占 / 台架不通 | 返回"未下发 · 无法确认现状"，**不假装已存在、也不假装已下发** | 把环境问题伪装成业务结果 |
| R3 | 下发后不回确认 | 返回"已下发 · 确认未收到"，不伪装成功 | 观测撒谎 |
| R4 | 传非法地址（5 位） | 返回"参数非法"，且**不动默认表** | 静默动到不该动的表 |
| R5 | 同一地址连跑两次 | 第二次"未下发（已存在）"，无报错 | 连跑两次结论不一致 |

R1、R2 是必须项。

---

## 8. 明确不做什么

- **不判定通过 / 失败**（调用方的事）；
- **不读档案表内容**（查询块的事）；
- 不判断能否抄到表（抄表块的事）；
- 不判断组网是否达标（组网块的事）；
- 不删档（删档块的事）；
- 不猜默认表地址（只在调用方完全没给时用配置默认值）。

---

## 9. 调用方义务（必须写进用例规范）

判据搬到调用方之后，保护不会自动发生。因此：

> **凡以"建档成功"为目的的用例，`archive.add` 之后必须显式接一次档案查询并声明"期望含该地址"。**
> 只跑 add 不跑 query 的用例，视为缺判据，不得入库。

否则"回了确认但没落地"这个假 PASS 会重新出现。

## 10. 与当前实现的差异（待改代码）

本文写的是**目标契约**。现有代码仍是旧口径，差在四处：

| 差异 | 现状 | 目标 |
|---|---|---|
| 谁来判 | 块内自己判"含地址→通过、明确不含→失败、查不全→说不清" | 块只报观测，判据搬到调用方 |
| 回查归属 | 回查档案表在块内完成 | 拆给独立查询块，由用例显式编排 |
| 返回形态 | 四种结论（通过/失败/说不清/台架不具备） | 两件事：是否下发（含原因）+ 确认是否收到 |
| 引用方 | 现有 5 条用例只跑本块就得到了"建档成功" | 必须补一步"查询 + 期望含"才算完成验证 |

**改代码之前，本文档描述的契约不生效**；现有代码行为以代码为准。审过之后一并迁移。
