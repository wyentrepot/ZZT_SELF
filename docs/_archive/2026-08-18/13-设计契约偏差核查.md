## 1. 结论

| 分类 | 数量 | 处理原则 |
|---|---:|---|
| 真实未闭环 | 4 | 保留设计要求，进入任务 2 收口清单 |

核心架构没有偏离：依赖方向、无 UI 编排、三源 Evidence、追加冻结、用例指纹和资源租约均已落地。当前真正影响 FR-5 完整性的缺口是 Run 状态模型未统一、Run 级 `inconclusive` 未落地、Artifact 未形成审计闭环，以及错误响应没有统一结构。

## 2. 真实未闭环（4 项）

### D-01 workbench RunStatus 声明与实际写入不一致（P0）

- 规范模型：`libs/test_automation.models.RunStatus` 包含 `created/queued/running/cancelling/cancelled/passed/failed/inconclusive/error`。
- workbench 投影：`apps/workbench/orchestration/models.py` 仍声明 `pending/running/passed/failed/aborted`。
- 实际执行器还会写入 `cancelling/cancelled`；`aborted` 未被执行器使用。
- 结论：真实契约漂移。应让 workbench 复用规范枚举，或建立显式兼容映射；不得继续依赖数据库绕过模型校验。

### D-02 Run 级结论缺少 inconclusive（P0）

- 总需求 FR-5 要求必要证据缺失时为 `inconclusive`。
- workbench `Report.verdict` 只有 `pass/fail`；runner 在 listener 证据为空、monitor/stimulus 被跳过时仍只能汇总为 pass/fail。
- 结论：真实功能缺口。应先定义“必要来源”判定规则，再把 Report、Run 状态和前端展示一起扩展为 `inconclusive`。

### D-03 Artifact 审计链未落地（P1）

- `libs/test_automation.models.Artifact` 已定义 SHA-256 等字段，但执行路径没有创建规范 Artifact。
- workbench Report 的 `artifacts` 只是日志路径字符串，无登记清单、内容摘要和下载接口。
- 结论：FR-5 的 Report 已落地，Artifact 部分未完成。需生成 manifest、登记哈希并通过逻辑 Artifact ID 下载。

### D-04 错误响应没有统一结构（P1）

- 当前 API 使用 FastAPI 默认 `HTTPException(detail=...)`。
- 骨架要求可机读的 `code/message/details/request_id`，并禁止泄漏本机路径和句柄。
- 结论：NFR-7 尚未闭环。应增加统一异常处理器，同时兼容前端现有错误展示。

## 3. 已澄清的设计口径（6 项）

以下差异不是必须改代码的缺陷，已在 `docs/03-骨架设计.md` 中区分“规范领域模型”和“当前兼容实现”。

### C-01 Report summary

`libs/test_automation.Report` 保留规范 `summary`；workbench 交付投影使用 `sources/flow_compare/feedback/verdict` 提供等价视图。后续做模型统一时转换，不要求为字段同名而破坏现有报告兼容性。

### C-02 API 前缀

已交付接口为 `/api/run*` 与 `/api/scenarios`，继续作为兼容接口。原 `/api/automation/*` 不再被描述成当前已实现路径；未来增加 Evidence 分页与 Artifact 下载时可提供规范别名。

### C-03 listener 索引状态

当前稳定状态为 `idle → queued → indexing → completed`，失败为 `failed`。骨架已按实际值修订；原 `ready/error` 是早期抽象，不要求代码改名。

### C-04 module_log 串口会话状态

当前稳定状态为 `idle/running/error`。它已满足运行独占和异常反馈；原 `closed/opening/open/closing` 粒度不是当前验收必需。

### C-05 XMODEM 烧录状态

实现已有 `starting → transfer → done/error`、`flashing` 占用位、明确成功返回和失败原因。它满足 FR-2；原 `preparing/verifying/succeeded` 只是不同命名，不再列为实现缺口。尚无协作式取消，因此骨架也不宣称支持 `cancelled`。

### C-06 sim_concentrator 任务状态

当前任务同步执行，以 `summary.verdict=pass/fail` 表达结果，并保留逐步证据。异步 `created/running/cancelled/error` 状态机不是当前接口能力；若以后异步化再单独设计。

## 4. 有意演进（2 项）

### E-01 Windows 串口网关已屏蔽

原 FR-9 已改列为总需求 CR-1，不属于当前交付范围，不参与验收统计。骨架只保留扩展说明，不得依赖尚不存在的 `serial_transport.py` 或 `windows_uart_bridge.py`。恢复时重新评审并分配正式 FR 编号。

### E-02 编排实现暂位于 apps/workbench/orchestration

规范领域模型、状态机、证据存储和资源租约位于 `libs/test_automation`；执行器与 RunStore 位于 `apps/workbench/orchestration`。后者没有 UI/static 依赖，可被 REST/测试复用，因此不违反“无 UI 编排”原则。是否下沉到 libs 属后续模块治理，不是当前阻塞项。
