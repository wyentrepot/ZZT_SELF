## 1. 项目概述

### 1.1 背景

公司产品由三部分构成：

- **CCO**（集中器通信单元）：与集中器通过串口交互，遵循 **13762 协议**（Q/GDW 10376.2 / DL/T 1376.2）；同时通过双模网络（电力线载波/微功率无线）与 STA 交互。
- **STA**（站点单元）：网络侧从节点，通过双模网络与 CCO 通信。
- **侦听台**：抓取网络层交互报文，对 HPLC/双模帧做深度解析与分钟级报表分析。

研发核心诉求是**缩短“改代码 → 验证 → 结论”的迭代周期**：固件修改后需要烧录、复位、观察运行日志、判定功能是否按预期运行；海量轮询/状态机日志淹没关键事件，人工核查效率低、结论不统一。

### 1.2 建设目标

建设一套**面向 AI 及工程师的闭环研发验证平台**：

```text
编码（代码修改）→ 编译/烧录 → 运行监控（事件化）→ 自动化验证（激励+断言）→ 结构化结论 → 归因反馈（喂回编码）
```

两条已建成的主能力线：

1. **事件监控（loghooks）**：配置 JSON 规则，从 CCO/STA 日志中提取完整运行流程（事件时间线、状态机路径、跨来源关联）。
2. **模拟集中器（sim_concentrator）**：在串口上自动执行 13762 帧交互（下发 → 接收 → 匹配 → 解析 → 逐步判定），返回结论 JSON。

**最终产品形态**：交付**一个集成程序**（platform 一体化工作台）——一个桌面入口、一个统一后端、一个页签式界面，把侦听台、模块日志/烧录、对照解析、模拟集中器与 AI 验证工作台全部集成，全链路在一个程序内闭环（FR-6）。

### 1.3 产品定位

侦听台是一套面向电力线载波（HPLC）抄表通信现场的 **“采集—解析—定位—验证”** 工具，帮助工程人员回答：

> 现场到底发生了什么？哪一帧、哪一个模块、哪一个协议字段或哪一个交互步骤出了问题？这个结论能否被复现和验证？

**非目标**：不替代现场集中器/CCO/STA 的生产控制系统；不负责电力营销、计费、档案或抄表数据管理；不以“自动给出绝对正确结论”为目标。

## 2. 用户与典型使用场景

| 用户 | 主要问题 | 使用路径 |
|------|----------|----------|
| 协议研发 | 某个报文或字段是否按协议实现 | 导入/采集日志 → 筛选帧 → 深度解析 → 查看原始帧与结构化字段 |
| 联调测试 | CCO、STA、集中器交互是否符合预期 | 实时监听或模拟集中器 → 执行场景 → 对照事件序列 → 查看差异 |
| 现场支持 | 现场故障发生在链路、模块还是协议层 | 选择日志 → 建索引 → 按 NID/时间/任务筛选 → 查看关联事件和分钟统计 |
| 模块开发 | 固件运行状态、烧录过程是否正常 | 模块日志页 → 观察 RX/TX 与状态 → 必要时 XMODEM 烧录 → 复核日志 |
| 项目负责人 | 当前能力、验证结果和遗留问题是什么 | 查看统一工作台中的场景运行记录、报告和需求状态 |

典型流程：

- **流程 A（现场日志定位）**：打开侦听台 → 选择日志 → 建索引 → 按 NID/任务/时间段/关键字筛选 → 帧详情展开协议层与嵌套报文 → 对照模块日志 → 导出原始帧与解析结果。
- **流程 B（验证协议或固件修复）**：选择场景 → 准备固件版本/提交号和串口配置 → 模拟集中器执行场景或接入真实设备 → 查看逐步期望/实际/差异 → 失败步骤下钻原始日志或报文 → 保存 Run 报告。
- **流程 C（模块维护与烧录）**：启动模块日志 → 确认 CCO/STA 通道状态 → 观察 RX/TX 和关键事件 → XMODEM 烧录 → 复核启动日志与协议交互 → 必要时跑最小回归场景。

## 3. 功能需求（FR）

### FR-1 侦听台（listener）—— 网络层交互抓取与解析

- **实时串口采集**：配置 COM 口和串口参数，接收连续字节流，切分 HPLC 帧（以 `7E` 为边界），落盘 `data/logs/` 并实时入库。
- **离线日志分析**：选择日志文件，流式建立 SQLite 索引（只扫描一次），支持进度、分页、筛选。
- **帧列表与筛选**：按序号、时间、NID、关键字分页查看摘要；每页最多 500 条。
- **单帧深度解析**：按需调用解析链（C# DLL + Python 富化），展示 FCH、MPDU、应用层、645/698 嵌套结构、解析警告与原始帧。
- **分钟采集分析**：识别 `APP_PORT=0x11` 且报文 ID `00E2/00E3/00E4` 的分钟采集帧；周期聚合（默认 15 分钟、时钟边界对齐、去重统计）；支持周期 1–1440 分钟自由输入、删除配置统计、任务轮次生命周期。
- **数据源互斥**：串口监听与日志文件分析运行时互斥（409），避免同一数据源竞态。
- **原始证据回看**：任何结构化字段必须能回到对应原始帧。

### FR-2 模块日志/烧录（module_log）

- CCO/STA 串口实时日志：按行加 `YYYYMMDD-HH:MM:SS:mmm` 时间戳，RX/TX/EVENT 分类落盘 `data/logs/模块/{cco|sta}/`。
- 同一串口上执行 **XMODEM 固件烧录**：常驻串口不关闭、RX 监控不停、动态切波特率。
- 三个页签：**实时日志 / 对照解析 / 模拟集中器**。
- 文件选择器（免手动输入路径）：Windows 原生文件对话框，上次路径持久化，中文路径 UTF-8 Base64 编码修复。
- 日志缓冲环形裁剪：后端内存 5000 行 + 前端 DOM 3000 行，防整夜 OOM。

### FR-3 事件监控（loghooks）—— 日志 → 完整运行流程

- **输入**：规则配置 JSON。来源可扩展：`module_log`（文本行）、`listener`（hex 帧）、`concentrator_10376`（13762 帧）。
- **匹配原语**：
  - `match`：单行/单帧触发（`text` 正则或 `field` 字段断言；`file`/`line`/`line_tolerance` 为弱约束）。
  - `sequence`：跨行状态流（如 STA 入网流程）。
- **规则组织**：按 `common`/`province` 隔离，全部 JSON 同时加载、自动识别省份；`--province` 仅作可选过滤。
- **输出**：事件流、分类摘要、状态机流程、跨来源关联、规则漂移清单、省份识别。
- **运行时接入**：module_log 写盘后异步调用；`LOG_HOOKS_ENABLED` 可开关；失败静默降级，绝不影响日志主链路。
- **CLI/REST**：`python -m loghooks scan <log>`、`python -m loghooks rules diff --old <a> --new <b>`、`/api/loghooks/scan|realtime|sources`。

### FR-4 模拟集中器（sim_concentrator）—— 流程 → 13762 自动交互

- **输入**：验证任务 JSON（若干步骤：`send` + `expect`/`expect_no_reply` + 超时；可选 `responders` 应答规则；`fail_fast`）。
- **输出**：结论 JSON（每步 sent_hex / matched / parsed / result / reason + 汇总 total/pass/fail/verdict）；CLI 退出码 0=pass、1=fail。
- **能力**：主动构帧下发、按 AFN/信封字段/嵌套 645/698 字段断言匹配、主动应答（内置规则 + 任务/步骤级覆盖）、逐步判定、REST/CLI 双入口、module_log 第三页签可视化。
- **边界**：帧格式统一走 `adapter_10376`；独立串口通道，不侵入 listener 只读监听。

### FR-5 AI 闭环编排层（Run / Report / 比对 / 反馈）

> 现状为“AI/工程师人工调用工具”；目标是由编排层把烧录→监控→激励→结论串成可追溯流水线。

- **FR-5.1 Run 抽象**：每次闭环验证 = 一个 `Run`，含 run_id、输入（commit/固件版本/烧录文件 hash/场景模板 id/参数）、执行（烧录 → 复位 → 监控 → 激励 → 比对 → 反馈）、产出（事件流摘要、验证结论、证据链）与归档（按 run_id/固件版本/场景检索）。
- **FR-5.2 统一验证报告（Report）Schema**：归一 loghooks 摘要、sim_concentrator 结论、侦听台分钟报表三类字段为一份报告（firmware、scenario、sources、assertions、verdict、artifacts、ts）。
- **FR-5.3 期望流程比对（流程投影）**：声明式期望流程（步骤 + 时间窗 + 可选步/分支），将实际事件流投影到期望流程，输出五类差异：✅ 命中、❌ 缺失、⚠️ 超时、🔀 顺序错乱、🚫 负向断言触发。
- **FR-5.4 归因反馈**：验证失败时，按可配置规则把结构化失败原因（缺失事件/超时/帧匹配失败/规则漂移）组装为给编码模型/工程师的反馈。

### FR-6 统一集成程序（platform）—— 全链路打通的最终形态

| 层 | 形态 | 说明 |
|----|------|------|
| 桌面入口 | pywebview 单窗口 | 复用现有 desktop 模式，一个 exe 即全部功能 |
| 统一后端 | 一个 FastAPI 主应用 | 挂载 listener app、module_log app、simcon app，并新增编排路由 |
| 前端 | 页签式 SPA | 侦听台 / 模块日志 / 对照解析 / 模拟集中器 / 验证工作台 |
| 编排层 | orchestration 子包 | Run 管理、场景模板、流程比对、归因反馈、报告归档 |
| 数据 | runs 库 + 报告归档 | `data/runs.sqlite` + `data/reports/{run_id}.json` |

设计原则：**不合并底层代码**（listener/module_log/sim_concentrator/loghooks 保持独立包、独立运行、独立测试）；**双模式并存**（独立服务 8765/8766/8781 为开发者模式，platform 统一入口为产品模式）；**编排能力零重实现**（复用既有引擎与 runner）。

### FR-7 共享协议解析层与基础设施

- `parser_service`：输入校验、解析调用与统一错误处理。
- `dotnet_parser`：封装 C# `GwHPLCAnalysis.dll`（V1.0.23），提供核心 HPLC 解析能力。
- `parser_lib` 适配器：`adapter_10376`、`adapter_645`、`adapter_698`、`adapter_dualmode` 覆盖主流帧格式；10376 可递归解析内嵌 645/698 帧。
- `shared.infra`：文件选择、目录浏览、运行时路径和通用基础设施。

### FR-8 工程化与交付

- **桌面 exe 打包**：listener / module_log 打包为 PyInstaller onedir 免安装产物（pywebview 内嵌窗口），保留网页模式。
- **一键启动**：根目录 `启动工具.bat` 统一菜单拉起（GBK + CRLF）。
- **一键打包发布（T-001，待实施）**：根目录 `一键打包-发布.bat`，产物输出到 `发布/侦听台/`，取代 `dist/`；打包后自动冒烟测试；拷贝到其他 Win10/11 电脑免安装运行。
- **目录分层**：`apps/`（listener / module_log / platform）+ `libs/`（shared / parser_lib / loghooks / sim_concentrator）+ docs / tools / reqs / data / legacy 归组。
- **测试基线**：全量 pytest 402 passed / 66 skipped（Windows+DLL 环境）；WSL 无 DLL 环境为 326 passed / 66 skipped / 9 DLL 失败（环境基线）。

## 7. 验收标准

### 7.1 侦听台（FR-1）

1. 选择日志后建立索引，支持分页（每页最多 500 条）、按序号/时间/字段筛选。
2. 点击单帧后才执行完整解析，结构化字段能回到原始帧。
3. 串口实时采集与日志文件分析互斥，冲突返回明确错误。
4. 分钟采集分析满足既定验收数值（如 50 条样本：23 条 E4、23 条 E4 全部满足 8 字节主动上报头 + 92 条内嵌 645 帧；默认 15 分钟周期统计数值与 API 断言一致）。
5. 真实大日志验收只做受控抽样或用户指定区间，不反复扫描原始大文件。

### 7.2 事件监控（FR-3）

1. 输入 CCO/STA 日志 + 规则 JSON，输出事件流/摘要/漂移清单；`rule_drifts` 非空时事件仍命中。
2. cco 规则不匹配 sta 日志、sta 规则不匹配 cco 日志（模块隔离）。
3. sequence 状态机在多节点并行日志中不串台（bucket 隔离）。
4. 跨来源关联以业务锚点（NID/冻结时刻）正确配对。
5. 规则命中率可量化，随版本回归可比对。

### 7.3 模拟集中器（FR-4）

1. 任务按步骤下发 → 接收 → 匹配 → 判定，结论 JSON 字段完整，verdict 与逐步结果一致。
2. 应答规则（内置 + 任务覆盖 + 步骤级）按预期生效。
3. `expect_no_reply` 场景正确判定（超时 pass / 收到帧 fail）。
4. CLI 退出码：pass=0、fail=1。
5. 与真实 CCO 联调（硬件在环）冒烟：入网/抄读/拉合闸等典型场景通过。

### 7.4 闭环与交付（FR-5 / FR-6 / FR-8）

1. 一次 Run 可串起 烧录 → 监控 → 激励 → 结论 → 报告，全部产物按 run_id 可检索。
2. 期望流程比对能输出缺失/超时/顺序错乱/负向触发四类差异。
3. 失败场景可生成归因反馈并回喂编码侧。
4. 报告含完整证据链（日志路径/帧 hex/规则版本/固件 commit）。
5. 双击一个 exe → 单窗口内含全部页签，各功能可操作、可切换。
6. `一键打包-发布.bat`：自动安装 PyInstaller → 打包 → 冒烟测试，退出码 0；产物在 `发布/侦听台/`，含 `侦听台.exe` 和 `_internal/`；拷贝到其他 Win10/11 电脑可直接运行；`dist/` 已移除。
7. 底层模块仍可独立运行与测试（全量 pytest 回归不破）。

## 8. 风险与待确认问题

### 8.1 主要风险

| 风险 | 影响 | 对策 |
|------|------|------|
| 规则维护成本随固件迭代上升 | 验证失效/漏检 | 命中率量化 + 漂移告警；rules diff 半自动闭环 |
| 13762 嵌套 645/698 字段级解析覆盖不足（OAD/OI 覆盖率 3.5%） | 深层次断言做不了 | 按业务优先级补 OAD；用真实抓包 golden data 回放 |
| 模拟集中器“不够真”骗不过 CCO 状态机 | 假通过/假失败 | 时序参数可配置；协议一致性测试；硬件在环冒烟 |
| 三时基不一致（模块时钟/PC 时钟） | 跨来源关联错位 | 以业务锚点（NID/MAC/冻结时刻/RTUA）关联 + 宽松时间窗 |
| 海量轮询日志噪音 | 事件流淹没 | 规则双重约束（file+msg）；阈值/聚合规则；分片落盘 |
| platform 挂载多应用串口冲突 | 同一串口争用 | 沿用 409 冲突约定，不做后端互斥锁 |
| 串口采集 2 天后卡顿 | 数据反复清空 + 死页膨胀 + 无索引 + 前端轮询 | 停止自动清库、VACUUM、补索引、keyset 翻页、批量写入、轮询瘦身（见性能分析文档） |

### 8.2 待确认问题

1. platform 统一入口端口（建议 8790）与页签顺序；桌面 exe 名称（如「AI 闭环工作台」）。
2. “输入 JSON 打印与事件名”的交付形态：规则文件 + 事件名映射表？可视化规则编辑器？
3. 验证场景库首期范围（建议：入网 / 分钟采集 / 拉合闸 / 搜表 / 远程升级）。
4. 归因反馈由谁消费：AI 编码模型（接口对接）还是工程师（报告阅读）？两者都要，接口先行。
5. 报告存储：SQLite（与现有索引一致）还是 JSONL 归档目录 + 索引？
6. 分钟采集帧结构 Q1~Q5 与代码 7 项问题需协议确认。
