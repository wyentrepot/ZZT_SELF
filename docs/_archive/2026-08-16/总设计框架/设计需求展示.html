AI 闭环研发验证平台 双模通信（CCO/STA）· 产品说明 v1.1

产品说明

本平台面向 HPLC/双模通信（CCO/STA） 固件研发场景，将「改代码 → 烧录 → 验证 → 结论」迭代周期从人工核查升级为 自动化闭环流水线。核心依赖四台设备：侦听台（网络层抓帧）、CCO/STA 模块（被测对象）、模拟集中器（13762 激励源）、上位机（运行平台工具）。

关键约束： ① 侦听台 只读监听网络层，不干扰 CCO↔STA 通信（观测面）； ② CCO 串口同时用于 日志采集 + 固件烧录（同端口复用，RX 监控在烧录期间不停）； ③ 模拟集中器使用 独立串口（COM4），不与 CCO 串口冲突（激励面）； ④ 三时基不一致（模块时钟 / PC 时钟 / 串口时间戳）——以 业务锚点（NID/MAC/冻结时刻/RTUA）关联 + 宽松时间窗补偿。

3 CCO 烧录 → 事件匹配（loghooks）

一条完整的"烧录 → 事件匹配"链路 核心流程

1
编译固件 → XMODEM 烧录到 CCO
上位机通过 module_log 串口（COM3）以 XMODEM 协议将 fw_v2.3.2.bin 分帧写入 CCO Flash。RX 监控在烧录期间不停，烧录过程日志同步落盘。
2
复位 CCO → 模块打印运行日志
CCO 上电复位后，固件通过串口持续输出 C 语言 printf 调试信息（如 "nwk disc done"、"onnet cnt = 1"）。module_log 按行加 YYYYMMDD-HH:MM:SS:mmm 时间戳，分类落盘 LOG/模块/cco/。
3
loghooks 规则匹配 → 事件流
加载规则文件 rules/anhui.json（text/field 正则 + sequence 状态机），扫描日志文件，输出结构化事件流：
· event network.onnet | 入网节点数 = 1 | aps_ioctrl_nwk.c:950
· event join.sta.ok | STA 入网成功 NID=0x61475d | sequence 4/4
· event collect.minute | 冻结时刻 10:00 | 12 只表
如 行号漂移（实际 line 超出容差），事件仍命中，但输出 rule_drifts 清单提示维护。
4
跨来源关联：侦听台帧 + 模块日志事件 + 集中器激励
以 NID=0x61475d、冻结时刻 10:00 为锚点，将侦听台抓取的网络层帧（含冻结数据 hex）与 loghooks 事件（含冻结时刻摘要）自动配对，验证：
· 模块日志声称"12 只表分钟上报" ↔ 侦听台帧实际包含 12 条 645/698 嵌套帧
· 模拟集中器下发的 10H-F1 读冻结命令 ↔ CCO 应答的 90H 帧（AFN/SEQ/RTUA 匹配）

4 AI 闭环验证 + 模拟集中器

模拟集中器：13762 自动激励与断言 已实现

  • 输入：验证任务 JSON — 若干步骤，每步 = send（下发帧，AFN/SEQ/RTUA/PW + 嵌套 645/698）+ expect（期望应答帧断言）+ 超时 + 可选 expect_no_reply
  • 执行：串口 COM4（独立于 CCO 串口），按步骤构帧→下发→等待→匹配→解析→判定
  • 输出：结论 JSON — sent_hex / matched / parsed（信封字段 + 数据项 + 嵌套帧）/ result（pass|fail）/ reason；汇总 total/pass/fail/verdict。CLI 退出码 0=pass、1=fail，供 AI 脚本判断
  • 应答引擎：内置规则表 + 任务/步骤级覆盖，模块上行自动回下行，无需人工干预
  • 可视化：module_log 第三页签人工监督同一串口

AI 闭环编排层：一次 Run 串起全链路 目标（P0）

  • Run 抽象：每次闭环验证 = 一个批次（run_id），包含：输入（commit/固件/场景模板 id/参数）→ 执行（烧录→复位→事件监控→激励→断言）→ 产出（事件流摘要 + 验证结论 + 证据链）→ 归档可检索
  • 期望流程比对：声明式描述期望流程（步骤序列 + 时间窗 + 分支/可选步），实际事件流投影到期望流程 → 输出 ✅命中 / ❌缺失 / ⚠️超时 / 🔀顺序错乱 / 🚫负向触发
  • 归因反馈：失败时结构化归因（如"assoc err 出现 → 检查关联流程"），回喂编码模型 → 修复 → 再验证，形成闭环
  • 统一报告：归一 loghooks 摘要 + simcon 结论 + 侦听台分钟报表为一份 Report JSON，含完整证据链

5 如何跑针对性自动化测试

自动化测试的四种模式

模式触发方式被测对象覆盖范围典型命令
1. 事件监控 CLI / REST CCO / STA 固件 入网/采集/发送/信标/状态机全流程 python -m loghooks scan LOG/模块/cco --province anhui --correlate LOG/侦听台
2. 模拟集中器 CLI / REST CCO 串口侧（13762 协议栈） AFN 指令集（入网/抄读/拉合闸/搜表/升级） python -m sim_concentrator verify task.json --json
3. 全量单测 pytest 各模块 Python 层 402 passed / 66 skipped（基线） pytest（假串口注入，不依赖硬件）
4. 闭环 Run（目标） REST / platform 工作台 CCO/STA 固件 + 协议栈 烧录→监控→激励→报告 全链路 POST /api/run {"scenario":"minute_collect_anhui","firmware":"v2.3.2"}

典型场景：针对"安徽分钟采集"做一次自动化闭环验证

1
准备阶段
输入：固件 v2.3.2（commit 9f2e1a）· 场景模板 minute_collect_anhui · loghooks 规则 rules/anhui.json · 验证任务 task_minute_collect.json
2
烧录 + 复位
module_log.flash_module("fw_v2.3.2.bin", port="COM3") → XMODEM 分帧写入 → 校验 SHA256 → 复位 CCO
3
运行监控（事件化）
loghooks.scan("LOG/模块/cco", rules="anhui", correlate="listener") → 扫描模块日志 → 输出 42 条事件 → 跨来源关联侦听台帧，锚点 NID 配对
4
激励验证（断言）
sim_concentrator.verify("task_minute_collect.json", port="COM4") → 5 步下发/应答/断言 → 全部 pass → verdict: pass
5
期望流程比对 + 结论
实际事件流 vs 期望流程（入网 + 分钟上报 [30s 窗]）→ ✅4 命中 · ❌0 缺失 · ⚠️0 超时 · 🚫0 负向
→ 统一报告 run-20260814-0003.json 归档，证据链完整（日志路径 + 帧 hex + 规则版本 + 固件 commit）
6
（如有失败）归因反馈
如 track_succ 缺失 → 归因："track done.*succ 未出现，检查关联流程" → 回喂编码侧 → 修复固件 → 重跑 Run
