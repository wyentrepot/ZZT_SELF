## 3. 产物格式（oad.json 条目 schema）

每个 OAD 条目为一个 key → dict，key 为 **8 位十六进制大写 OAD**（= OI 4位 + 属性 2位 + 索引 2位）。
本轮以 **OI 级注册**为主：对每个缺失 OI 注册一条 `{OI}0000`（属性 00 / 索引 00）即可；已有属性/索引细分的条目保持不变。

```json
{
  "30020000": {
    "name": "电能表过压事件",
    "data_type": "record",
    "unit": null,
    "scale": 0,
    "desc": "过压事件记录（事件类 OI=3002）"
  }
}
```

字段约定（对齐现有条目）：
- `name`：中文对象名（取附录 A 名称，去多余空格；可补「-总/A相」等区分）
- `data_type`：DL/T 698.45 数据类型枚举（参考现有值：`array` / `record` / `octet-string` / `visible-string` / `long-unsigned` / `double-long` / `double-long-unsigned` / `date_time_s` 等；拿不准用附录 A 对应类的常规类型，事件/记录类用 `record`）
- `unit`：单位字符串；无量纲用 `null`
- `scale`：小数位（整数，默认 0）
- `desc`：简短中文说明，可含 OI/IC/类别信息便于追溯

## 4. 执行步骤（hy3 机械补全）

1. 读取协议 md 附录 A，提取全部 515 个 OI（OI/名称/IC/类别）。
2. 对比 `oad.json` 现有 19 个 OI，找出缺失的 497 个。
3. 对每个缺失 OI 生成 `{OI}0000` 条目（属性/索引=00），填 name/data_type/unit/scale/desc。
4. 将新条目**合并**进 `oad.json`（保留现有 52 条，不删除、不覆盖已有 key；JSON 保持 UTF-8、缩进与现有风格一致）。
5. 运行 `python tools/scripts/analyze_oad_coverage.py` 验证覆盖率提升（目标 ≥ 99%）。
6. 输出交付摘要：新增条数、剩余缺失（若有，需说明原因）。

## 5. 语义复核（deepseek-v4-flash）

对 hy3 补全后的 `oad.json` 做**协议语义复核**，重点：
1. OI ↔ 名称是否与附录 A 一致（无错位、无串类）。
2. `data_type` 是否符合该对象在协议中的数据类型（电能/需量/冻结类多为数值型，事件/记录类为 record）。
3. `unit`/`scale` 是否合理（电能 kWh、功率 kW、电压 V、电流 A、频率 Hz、时间 s 等）。
4. 抽查至少 10% 条目对照附录 A 原文。
5. 输出复核报告：发现的问题条目清单（key + 修正建议）+ 结论（通过/需修正）。
