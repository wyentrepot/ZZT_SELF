# 侦听台改造项目骨架设计

> 本文只定义模块职责、输入输出、交互协议、目录和核心数据模型。需求依据见[总需求](02-总需求.md)，进度见[任务安排](04-任务安排.md)。

## 1. 分层与目录

```text
apps/
├── listener/                 # 侦听采集与报文分析
├── module_log/               # 模块日志与烧录
└── workbench/                # 统一入口与自动验证 API/UI
libs/
├── shared/                   # 基础设施及 .NET 解析桥接
├── parser_lib/               # 独立协议解析库
├── loghooks/                 # 配置驱动的日志事件引擎
├── sim_concentrator/         # 1376.2 模拟集中器
└── test_automation/          # 目标：无 UI 的验证编排内核
data/
├── logs/
└── runs/<run_id>/
skills/
└── observe-workbench-logs/ # P2 计划中的项目内、未安装 AI 观察技能源码
    ├── SKILL.md
    ├── agents/openai.yaml
    └── scripts/workbench_ai_client.py
```

依赖方向为 `apps → libs`；验证内核只依赖各模块公开适配器和领域模型，不导入 Web 页面或桌面壳。

## 2. 模块契约

| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| listener | 文件/串口采集、索引、解析、业务分析 | 路径、串口配置、原始帧、查询条件 | 帧证据、分页与分析结果 |
| module_log | 串口日志、状态与 XMODEM 烧录 | 串口配置、固件、控制命令 | 日志、烧录进度、资源状态 |
| parser_lib/shared | 校验、协议选择、DLL/Python 解析适配 | 原始字节、协议提示 | 统一解析结果或结构化错误 |
| loghooks | 规则校验与日志事件识别 | 日志流、规则集 | 事件证据、规则诊断 |
| sim_concentrator | 1376.2 通信和步骤流程 | 端口、设备上下文、流程计划 | 步骤证据、响应或错误 |
| test_automation | 用例、资源、Run、断言、报告 | 用例包、适配器、参数 | Evidence、AssertionResult、Report |
| workbench | API 聚合、操作入口与展示 | HTTP/UI 操作 | 状态、证据下钻、报告下载 |

## 3. 核心数据模型

本节定义 `libs/test_automation` 的规范领域模型，是新用例、持久化和外部复用的目标契约。`apps/workbench/orchestration` 的 Run 状态已复用规范枚举（2026-08-18，D-01，初态 created，不再有 `pending`）；`sources/flow_compare/feedback` 报告视图仍为兼容投影，不得反向改变规范模型。

```text
Run {
  id, case_id, case_version, case_fingerprint,
  status: created|queued|running|cancelling|cancelled|passed|failed|inconclusive|error,
  created_at, started_at, finished_at, parameters, resource_leases, error
}

Evidence {
  id, run_id, kind: frame|event|interaction|measurement|log,
  source, observed_at, sequence, correlation_key,
  payload, raw_ref, metadata
}

AssertionResult {
  id, run_id, assertion_id,
  outcome: pass|fail|inconclusive,
  expected, actual, evidence_ids, message
}

Report { run_id, summary, steps, assertions, evidence_index, artifacts }
Artifact { id, run_id, type, path, sha256, created_at }
```

Run 终态不可回退，测试不满足与系统错误分离。Evidence 追加写入，`raw_ref` 指向不可变原始内容或摘要。Report 是派生结果，Evidence 与 Artifact 清单是审计基础。

## 4. 用例与执行流程

用例包包含清单、参数、资源要求、步骤、断言和版本信息；加载时计算不可变指纹。

```text
发现并校验用例 → 创建 Run → 获取资源租约 → 启动适配器
→ 执行步骤并收集 Evidence → 冻结证据窗口 → 执行断言
→ 生成 Report/Artifact → 释放资源
```

取消先进入 `cancelling`，适配器幂等清理后进入 `cancelled`。清理失败写入错误，但不得删除已有证据。

## 5. 适配器协议

```python
class SourceAdapter:
    def start(self, run_context): ...
    def collect(self, evidence_sink): ...
    def stop(self): ...
    def health(self): ...
```

实现可同步、异步或使用后台线程，但 `stop()` 必须幂等，源错误必须转换为统一错误类型。硬件端口由资源租约独占，离线文件可共享只读。

## 6. API 骨架

### 6.1 当前已实现兼容接口

| 方法与路径 | 用途 |
|---|---|
| `GET /api/scenarios` | 列出场景模板 |
| `POST /api/run` | 创建并异步启动 Run |
| `GET /api/run/{id}` | 查询 Run 状态 |
| `POST /api/run/{id}/cancel` | 请求取消 |
| `GET /api/run/{id}/report` | 获取报告及内嵌证据下钻数据 |
| `GET /api/runs` | 列出历史 Run |

以上路径是已交付兼容接口，不应直接改名。规范化 API 可在保持兼容别名的前提下演进。

### 6.2 尚未闭环的接口契约

- Evidence 当前随 Report 内嵌返回，尚无独立分页接口。
- ~~Artifact 尚无登记、校验和下载接口~~ → ✅ 已闭环（2026-08-18，D-03）：`Report.artifacts` 结构化（逻辑 ID + SHA-256 manifest），`GET /api/run/{run_id}/artifacts` 列表与 `/{artifact_id}` 下载接口 + 路径越界防护。
- ~~FastAPI 默认 `detail` 错误尚未统一为 `code`、`message`、`details`、`request_id`~~ → ✅ 已闭环（2026-08-18，D-04）：`errors.py` 全局处理器统一结构并保留 `detail` 兼容前端。
- 所有接口均不得泄漏线程对象、串口句柄或本机绝对路径。

### 6.3 P2 项目内 AI 观察技能与客户端（计划契约）

`skills/observe-workbench-logs/` 是随仓库评审的技能源码，不是个人 Codex
安装目录；`agents/openai.yaml` 固定
`policy.allow_implicit_invocation: false`，只能通过
`$observe-workbench-logs` 显式调用。请求、结果、匹配器和授权字段的单一事实
来源是[REQS §25](../reqs/0004-workbench-serial-sessions/REQS.md)；本节只固定
客户端与已实现 `/api/ai/v1` 的交互边界。

| 客户端命令 | 已实现方法与路径 | 只读/写入边界 |
|---|---|---|
| `status` | `GET /api/ai/v1/status` | 只读工作台、会话与操作状态 |
| `observe` | `POST /api/ai/v1/observations` | 仅对既有 module session 或既有 listener index/capture 创建观察 |
| `wait` | `GET /api/ai/v1/operations/{operation_id}/wait` | 只轮询既有 operation，不取消或停止来源 |
| `artifact` | `GET /api/ai/v1/artifacts/{artifact_id}` 或 `/content` | 只读取服务端登记的 Artifact |
| `listener-schema` | `GET /api/ai/v1/listener/schema` | 只读取可查询的帧语义与字段选择器 |
| `frame-detail` | `GET /api/ai/v1/listener/indexes/{index_id}/frames/{frame_id}` | 必须保留 `index_id + frame_id` 复合深链 |

客户端默认是 dry-run：仅输出规范化、脱敏的请求计划，不访问工作台且不创建
operation。只有显式 `--execute` 才允许发出 HTTP；其中 `observe` 的
`POST /observations` 必须同时具备既有目标和明确执行意图。Token 唯一来自
`WORKBENCH_AI_TOKEN`，不得作为参数、配置值、输出、异常文本或 URL 用户信息
出现；base URL 仅允许规范化的本机工作台地址。

`wait` 每次服务端等待不超过 30 秒，并在 `matched`、`succeeded`、
`timed_out`、`cancelled`、`source_stopped`、`error` 或 `interrupted` 时停止。
结果必须保留服务端 Artifact 逻辑 ID；listener 命中必须保留复合键及其
detail/UI 深链。客户端以稳定 JSON 输出成功计划或结果，并以可读、脱敏的
错误和非零退出码表示失败。

该技能及客户端不得提供或隐藏 `ensure`、`start`、`stop`、`send`、`flash`、
烧录、串口打开或任意文件系统路径扫描能力；不得安装到个人目录，也不得产生
硬件副作用。

### 6.4 [REQS-0021](../reqs/0021-ai-capability-gateway/REQS.md)：AI 能力任务门面 v2（计划契约）

现有 `/api/ai/v1` 是面向专家调用方的细粒度兼容控制面；它和页面子应用路径
均继续保留，不能通过重命名或删除来换取“接口数量减少”。`/api/ai/v2` 是新增
的任务级门面：它只编排已存在的服务、索引和操作，不通过 HTTP 回调自身，也不
重写模块日志、侦听台或模拟集中器的领域逻辑。

`observe-workbench-logs` 技能仍是只读、默认 dry-run 的项目内客户端，边界保持
§6.3 不变；v2 是受审计的服务端 API，服务于获明确授权的本机 AI 工作流，两者
不得互相放宽写操作限制。

| v2 路径 | 任务职责 | 兼容/安全边界 |
|---|---|---|
| `GET /api/ai/v2/capabilities` | 返回可用后端、资源、能力版本和调用方可执行动作 | 不返回 token、串口句柄或绝对路径 |
| `POST /api/ai/v2/investigations` | 并行组织模块日志、侦听台和 simcon 的结构化观察/查询 | 只复用既有 index、store、trace、observation 读取能力 |
| `POST /api/ai/v2/verification-runs` | 组织既有 simcon 验证并归一结果 | 不新建确定性 VerificationEngine，不改变现有 Run 口径 |
| `POST /api/ai/v2/module-actions` | 以判别式 `ensure`、`send`、`stop` 执行模块动作 | 仅允许显式 action；禁止任意 action/payload 透传 |
| `POST /api/ai/v2/flash-jobs` | 创建独立烧录任务 | 保留固件目录白名单、幂等和不可取消约束 |
| `GET /api/ai/v2/jobs/{job_id}?wait_seconds=0..30` | 读取或等待统一 job 状态 | GET 不推进或写入 job 状态 |
| `POST /api/ai/v2/jobs/{job_id}/cancel` | 取消可取消任务 | 烧录、不可取消验证保持拒绝取消 |
| `GET /api/ai/v2/jobs/{job_id}/evidence?level=L1|L2|L3` | 按层读取诊断证据 | L3 只经稳定引用获取原始内容 |

v2 的所有请求和响应必须使用命名 Pydantic 模型，禁止以 `dict[str, Any]` 作为
公开契约。至少定义 `AccessContext`、`Capability`、`JobEnvelope`、`EvidenceRef`
和来源判别联合。`JobEnvelope.job_state` 只描述机械执行状态；仅验证/观察类
任务可带 `verdict=pass|fail|inconclusive|error`，模块发送和烧录不得把“写入成功”
伪装为业务 `pass`。

三源原始语义不合并为一张万能表。统一的是 `source`、`window`、稳定关联键、
来源健康度、证据引用和分页边界；module_log、listener、simcon 仍各自保留特有
字段。默认结果为 L1（1--3 KB 摘要）；L2 上限为 16 KB 或 50 条证据；L3 只按
`evidence_id`、`raw_ref`、`index_id + frame_id` 等稳定引用下钻。历史 listener
查询必须绑定原始 `index_id`；实时 `not_seen` 在无可信到达时间时只能是
`live_window_unverified`/`inconclusive`，不能作为缺失证明。

访问域以实际 socket 对端地址判定，绝不信任 `X-Forwarded-For`。在显式配置
`WORKBENCH_LOCAL_FULL_ACCESS=1` 时，`127.0.0.1`、`::1` 和测试客户端可调用
全部 v2 能力且仍写审计；管理员授权签发/撤销仍要求现有本机 + admin key。非
loopback 的 v2 调用须走 Bearer grant 的 capability/scope/resource 检查。本需求
首期不改造旧页面和 v1 路由的局域网访问策略，因而不得声称已完成全局 LAN 收敛。

服务端 job 需记录“创建/复用”的资源所有权。仅 job 自己创建的会话或 listener
可在 `cleanup=owned_only` 下自动关闭；复用的页面或其他任务资源绝不自动 stop/
close。异步状态由后台执行器或来源回调推进，读取 job 不得成为完成烧录或观察的
唯一推进机制。

## 7. 持久化、并发与界面

- 元数据可存 SQLite；Evidence 使用追加式 JSONL 或等价顺序存储。
- 同一 Run 的 `sequence` 单调递增；写入立即刷新，冻结后拒绝追加。
- RunStore 原子校验状态迁移；资源租约以资源类型和稳定标识为键。
- 大文件通过索引和分页访问；原始数据与派生数据分目录保存。
- 工作台用页签组合功能，核心状态来自 API 和持久化，浏览器内存不作为权威状态。

## 8. 子系统状态机

| 对象 | 合法主路径 | 异常/恢复约束 |
|---|---|---|
| listener 日志索引 | `idle → queued → indexing → completed` | 失败进入 `failed`；重新导入可重建索引，原日志不变 |
| module_log 串口会话 | `idle → running → idle` | 打开异常抛出并保持原状态；读取异常进入 `error`；同一通道运行时重复启动返回现有状态 |
| XMODEM 烧录 | `starting → transfer → done/error` | `flashing` 表示占用中；`done` 明确成功，`error` 携带失败原因；最终清理响应队列 |
| sim_concentrator 端口 | `closed → opening → open → closing → closed` | 流程任务只能绑定 `open` 端口 |
| sim_concentrator 单次任务 | 同步执行，结果由 `summary.verdict=pass/fail` 表达 | 每一步保留请求、响应与判定；当前不提供异步取消和任务级持久状态 |

子系统状态通过适配器映射到 Run，不把底层状态直接当作 Run 终态。完整转换规则应由相应模块测试锁定。

## 9. 实体关系与接口全局约定

- CasePackage 以 `case_id + version + fingerprint` 唯一确定，可产生多个 Run。
- Run 拥有 Evidence、AssertionResult 和 Artifact；Report 对它们做只读汇总。
- Evidence 可被多个 AssertionResult 引用，但不得在断言后改写。
- 所有时间使用带时区 ISO 8601；ID 为稳定字符串；列表接口必须分页。
- 写接口支持请求关联标识；重复取消与停止操作必须幂等。
- 对外路径使用逻辑 Artifact ID，服务端负责解析真实路径并防止目录穿越。
- API 兼容性变更必须显式版本化；当前历史 OpenAPI/Schema 快照仅供归档参考。
