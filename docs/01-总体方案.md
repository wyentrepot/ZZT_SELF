# 侦听台改造项目总体方案

> 本文只定义项目目标、系统边界、最终形态与总体架构。功能条款见[总需求](02-总需求.md)，模块契约见[骨架设计](03-骨架设计.md)，实施状态见[任务安排](04-任务安排.md)。

## 1. 建设背景

现有侦听、模块日志、协议解析、模拟集中器和验证工具已经形成独立能力，但数据、操作入口和验证结论相互割裂。现场问题需要人工在报文、模块日志和交互流程之间对时、比对，修复后也缺少可重复执行、证据可追溯的回归闭环。

本项目把这些能力整合为面向 HPLC 抄表通信研发与验证的统一工作台，使需求或故障沿“需求—用例—采集—解析—断言—证据—报告”闭环流转。

## 2. 最终效果

- 从一个工作台完成侦听分析、模块维护、日志事件分析、模拟集中器交互和自动验证。
- 国网、南网及业务扩展协议由共享解析能力统一支撑，原始数据始终可追溯。
- 三类数据源统一转换为带时间、来源和关联标识的证据，各采集模块仍可独立运行。
- 用例可重复执行，结论区分通过、失败和证据不足，并能下钻到原始证据。
- 开发环境与 Windows 硬件运行环境解耦，形成可测试、可打包、可交付的工程。

## 3. 系统边界

### 3.1 系统负责

- 侦听台报文的实时采集、离线导入、索引、解析和业务分析。
- 模块串口日志采集、固件烧录和关键事件提取。
- 模拟集中器的 1376.2 交互、流程驱动和响应验证。
- 测试用例加载、资源协调、证据归一、断言执行和报告生成。
- 统一工作台、统一运行入口和工程化交付。

### 3.2 系统不负责

- 替代生产主站、集中器或现场设备承担生产控制职责。
- 修改或重新定义国网、南网协议原文。
- 让 AI 在无证据时自行判定测试通过。
- 将所有模块强耦合为一个不可独立测试或运行的进程。

## 4. 总体架构

```text
统一工作台 apps/workbench（逐步演进为 platform）
├── 侦听与分析 apps/listener
├── 模块日志与烧录 apps/module_log
├── 自动验证编排层
│   ├── 用例目录与计划
│   ├── 资源租约与 Run 执行
│   ├── 统一断言
│   └── Report / Artifact
└── 共享能力 libs/
    ├── shared / parser_lib       协议解析与基础设施
    ├── loghooks                  日志事件提取
    └── sim_concentrator          模拟集中器交互
```

架构采用“独立数据源 + 无 UI 编排内核 + 统一入口”。采集模块对外提供标准适配接口，编排层只依赖契约，不依赖具体页面；工作台负责展示和操作，不承载核心判定逻辑。

## 5. 核心原则

1. 原始数据不可丢失，结构化证据必须能够反查来源。
2. 测试结论由明确断言和证据产生；证据缺失不能等同于失败。
3. 协议解析、数据采集、验证编排和界面展示分层演进。
4. listener、module_log、loghooks、sim_concentrator 保持可独立测试。
5. 先打通最小闭环，再扩充协议覆盖、复杂场景和智能辅助。

## 6. 演进路线

- 阶段一：冻结 Run、Evidence、Assertion、Report 等核心契约，打通单用例闭环。
- 阶段二：接入三类真实数据源并迁移现有 GW-CASS 测试资产。
- 阶段三：完善统一工作台、证据下钻、报告归档与一键交付。
- 阶段四：在稳定证据链之上增加 AI 辅助生成、归因与回归建议。
