# 13. 设计契约偏差核查（01 总体方案 / 02 总需求 / 03 骨架设计 vs 当前实现）

> 核查日期：2026-08-18
> 核查范围：`docs/01-总体方案.md`、`docs/02-总需求.md`、`docs/03-骨架设计.md` 三份设计文档，对照当前 `master` 代码（commit `cdadb09`）。
> 目的：识别实现与初始设计之间的偏差，区分「有意演进」与「真实漂移」，为后续修正或设计修订提供依据。
> 原则：本文只记录偏差与建议，**不改动任何设计文档**；修正动作经评审后另行立项。

## 1. 核查结论概览

| 结论 | 数量 |
|---|---|
| 明确偏差（实现与设计不符，建议修正或修订设计） | 10 |
| 有意偏差（决策已记录，不视为问题） | 2 |
| 一致项（实现符合设计） | 8 |

总体判断：**核心架构原则（apps → libs 依赖方向、无 UI 编排内核、证据可追溯、模块可独立测试）均落地**；偏差集中在「编排层状态/报告模型的字面量简化」「子系统状态机字面量未按骨架 §8」「API 前缀与错误格式未按骨架 §6」「Artifact 未生成」四类。多数偏差为**演进中的简化**，不破坏闭环能力，但**模型字面量与 runner 实际写入不一致**（workbench RunStatus）是必须修复的真实漂移。

## 2. 明确偏差（10 项）

### 2.1 workbench RunStatus 模型与骨架 §3 不符且与 runner 实际行为矛盾 【真实漂移 · 需修复】

- **文档要求**（03 §3）：`Run.status: created|queued|running|cancelling|cancelled|passed|failed|inconclusive|error`
- **实际**（`apps/workbench/orchestration/models.py`）：
  ```python
  RunStatus = Literal["pending", "running", "passed", "failed", "aborted"]
  ```
- **矛盾点**：`runner.py` 实际写入 `"cancelling"`、`"cancelled"`（取消 Run 功能，已测试锁定），且 API 层也返回 `"error"`；但模型 Literal 不含这些值、含从未使用的 `"aborted"` 与 `"pending"`（store 初值）。DB 层不经过 pydantic 校验故未报错，但**模型声明是错的/过时的**。
- **影响**：模型即契约，CLI/REST/AI 三端复用时状态值域不一致；OpenAPI schema 会展示错误的状态集；`inconclusive` 语义无法在编排层表达。
- **建议**：workbench 编排层直接复用 `libs/test_automation/models.py::RunStatus`（9 态完整），删除本地简化 Literal；或至少将 Literal 改为 `pending|running|cancelling|cancelled|passed|failed|inconclusive|error` 并去掉 `aborted`。

### 2.2 Report 缺 `summary` 字段（骨架 §3） 【轻微 · 可补或修订设计】

- **文档要求**（03 §3）：`Report { run_id, summary, steps, assertions, evidence_index, artifacts }`
- **实际**（`apps/workbench/orchestration/models.py::Report`）：用 `sources` / `flow_compare` / `feedback` 结构替代，无 `summary` 字段。
- **影响**：报告缺统一概览字段；前端下钻面板基于 `evidence_index/evidence_detail` 工作，不依赖 summary，功能未受损。
- **建议**：补 `summary: Dict[str, Any]`（含各来源摘要 + verdict），或经评审后修订骨架 §3 的 Report 结构。

### 2.3 Report `verdict` 仅 `pass|fail`，无 `inconclusive`（骨架 §3 / FR-5） 【中等 · 需修复】

- **文档要求**（02 FR-5、03 §3）：证据不足产生 `inconclusive`，不得伪装为 `pass`/`fail`。
- **实际**：`verdict: Literal["pass", "fail"]`；`runner.py` 全部路径只产出 pass/fail。`libs/test_automation` 的 `ASSERTION_OUTCOMES` 含 `inconclusive`，但编排层从未把 Run 级结论判为 inconclusive。
- **影响**：违反 FR-5「证据不足产生 inconclusive」——来源缺失时（如 listener 库不存在）当前降级为空但结论仍是 pass/fail，未表达「证据不足」。
- **建议**：`verdict` 扩为 `pass|fail|inconclusive`；runner 在关键来源缺失/证据为空时落 `inconclusive`（与现「优雅降级不阻断」兼容：降级但结论标注 inconclusive）。

### 2.4 API 路径前缀不符（骨架 §6 `/api/automation/*` vs 实际 `/api/run*`） 【轻微 · 兼容性取舍】

- **文档要求**（03 §6）：`GET /api/automation/cases`、`POST /api/automation/runs`、`GET /api/automation/runs/{id}`、`POST /api/automation/runs/{id}/cancel`、`GET /api/automation/runs/{id}/evidence`、`GET /api/automation/runs/{id}/report`、`GET /api/automation/runs/{id}/artifacts/{id}`。
- **实际**（`apps/workbench/api.py`）：`GET /api/scenarios`、`POST /api/run`、`GET /api/run/{id}`、`POST /api/run/{id}/cancel`、`GET /api/run/{id}/report`、`GET /api/runs`、`POST /api/compare`、`POST /api/feedback`。
- **影响**：API 已前端联调并打包交付，改名破坏兼容；但骨架 §6 的 `automation` 前缀、evidence 分页接口、artifacts 下载接口未实现。
- **建议**：保留现有 `/api/run*` 为当前版本（避免破坏交付物），**新增**骨架要求的 `/api/automation/runs/{id}/evidence` 分页接口与 `/api/automation/runs/{id}/artifacts/{id}` 下载接口作为 v0.2 补充，并在设计层标注前缀差异为「已实现版本」。

### 2.5 错误响应未按骨架 §6 统一格式 【轻微 · 需补】

- **文档要求**（03 §6）：错误统一含 `code`、`message`、`details`、`request_id`，不得泄漏线程对象/串口句柄/本机绝对路径。
- **实际**：全部用 FastAPI 默认 `HTTPException(detail=...)`，无 `code/message/details/request_id`。
- **影响**：前端仅消费 `detail` 字符串；未泄漏敏感信息，但错误不可机读分类。
- **建议**：加统一异常处理器，输出 `{code, message, details, request_id}`，前端错误分支解析升级（不破坏现有 detail 消费）。

### 2.6 listener 索引状态机字面量不符（骨架 §8 `idle→indexing→ready`） 【轻微 · 语义命名】

- **文档要求**（03 §8）：`idle → indexing → ready`；失败进 `error`。
- **实际**（`apps/listener/log_service.py`）：`idle / queued / indexing / completed / failed`（`ready` 改为 `completed`，新增 `queued`）。
- **影响**：语义等价（completed=ready），但字面量与骨架不一致；测试按实际值锁定。
- **建议**：二选一——改代码为 `ready`（牵动前端/测试），或评审后修订骨架 §8 为 `idle|queued|indexing|completed|failed|error`。

### 2.7 module_log 会话状态机字面量不符（骨架 §8 `closed|opening|open|closing|closed`） 【轻微 · 语义命名】

- **文档要求**（03 §8）：串口会话 `closed → opening → open → closing → closed`；同一端口不得重复占用。
- **实际**（`apps/module_log/module_serial_service.py`）：`_state = idle | running | error`。
- **影响**：`running` 已含「常驻独占」语义（模块自身承诺 start 开一次、stop 才关），端口占用约束实际满足；但无 `opening/open/closing` 细粒度。
- **建议**：评审后修订骨架 §8（module_log 会话态简化为 `idle|running|error` 属合理简化），或按骨架补细粒度态。

### 2.8 XMODEM 烧录状态无显式字面量（骨架 §8 `idle|preparing|transferring|verifying|succeeded`） 【中等 · 需补】

- **文档要求**（03 §8）：`idle → preparing → transferring → verifying → succeeded`；取消 `cancelled`，异常 `failed`，最终释放串口。
- **实际**（`apps/module_log/module_serial_service.py`）：`_flash_state` 仅 `phase="transfer"` + `message="n/total"` 进度 + `flashing` 布尔，无 `preparing/verifying/succeeded` 阶段。
- **影响**：前端烧录进度展示可用，但「烧录是否成功」无显式状态位（靠 message/异常推断），不利于 FR-2「反馈成功或失败原因」的结构化表达。
- **建议**：`_flash_state` 增 `phase: idle|preparing|transferring|verifying|succeeded|failed|cancelled`，success 时显式置 `succeeded`。

### 2.9 sim_concentrator 任务状态无字面量（骨架 §8 `created→running→passed/failed/cancelled/error`） 【轻微 · 结构差异】

- **文档要求**（03 §8）：任务 `created → running → passed/failed/cancelled/error`，终态不可回退，每步保留请求/响应/判定证据。
- **实际**（`libs/sim_concentrator/runner.py::execute_task`）：返回 `{task_id, port, steps[], summary{total,pass,fail,verdict}}`，无任务级状态字段；每一步 `run_step` 有 `result=pass/fail`。
- **影响**：「每一步保留证据」已满足；任务级状态由 `summary.verdict` 隐式表达，无显式 `created/running/cancelled/error`。
- **建议**：评审后确认是否需要任务态字面量；当前以 `summary.verdict` 表达结论可接受。

### 2.10 Artifact 模型存在但未生成、无下载 API（骨架 §3/§6） 【中等 · 待落地】

- **文档要求**（03 §3）：`Artifact { id, run_id, type, path, sha256, created_at }`；Report 含 `artifacts`；§6 有 `GET /api/automation/runs/{id}/artifacts/{artifact_id}` 下载。
- **实际**：`libs/test_automation/models.py::Artifact` 类存在（含 sha256），但**无任何代码生成 Artifact 实例**；`Report.artifacts: List[str]` 仅字符串列表未承载 sha256；无下载 API。
- **影响**：FR-5「生成可归档 Report 和 Artifact」的 Artifact 部分未落地；报告 JSON 已归档，但「原始数据/产物的 sha256 校验清单」缺失。
- **建议**：在 runner 生成报告时，把关键产物（报告 JSON、输入日志、固件哈希）登记为 Artifact（含 sha256），并补下载接口。

## 3. 有意偏差（2 项，决策已记录，不视为问题）

### 3.1 FR-9 Windows 串口网关已屏蔽

- **文档要求**（02 FR-9、03 §11）：完整 Windows 串口网关 + WSL 虚拟串口。
- **实际**：任务 6 已屏蔽不排期（`docs/04-任务安排.md` 任务 6 状态「已屏蔽」）；`libs/shared/serial_transport.py` / `windows_uart_bridge.py` 契约是否已建需复核。
- **依据**：用户明确决策「任务 6 已屏蔽」，REQS-INDEX 0003 状态「⛔ 已屏蔽」。

### 3.2 验证编排内核分居两处（test_automation 领域模型 + workbench/orchestration 执行）

- **文档要求**（01 §4、03 §1）：`libs/test_automation` 目标是「无 UI 的验证编排内核」，只依赖模块公开适配器与领域模型。
- **实际**：领域模型/状态机/资源租约/证据存储确实在 `libs/test_automation`（无 UI 依赖 ✓），但 **Run 执行器（`runner.py`）与 store 在 `apps/workbench/orchestration/`**，test_automation 无 Run 执行。
- **影响**：「核心编排不得依赖 UI」已满足（orchestration 无 UI/静态依赖 ✓，可被 CLI/REST/AI 复用）；但「内核放 libs」的骨架设想未完全达成，编排执行器耦合在 workbench app 内。
- **依据**：演进中把执行器放 workbench 以便就近 API/UI，属工程取舍；建议评审后修订骨架 §1（或后续把 runner/store 下沉 libs/test_automation）。
