## 1. 背景与设计哲学

### 1.1 与上一版的区别

上一版（v1）设计为「紧耦合事件驱动」：三源规则互相等待、事件依赖解锁流程、compare 重构统一事件流比对。**过于复杂**。

本版（v2）核心哲学：**三源完全解耦，事件驱动只做「记录 + 导航」**。

```
模块日志(独立)     侦听台(独立)       模拟集中器(独立)
   │规则匹配          │帧规则匹配          │用例流程 + 事件规则
   ▼                  ▼                    ▼
 抄表事件            分钟采集事件          入网事件
   │                  │                    │
   └────────┬─────────┴─────────┬──────────┘
            ▼                    ▼
       事件驱动记录（总事件表）    ← 只记录 {时间, 事件名, 来源, 锚点}，无逻辑
            │
            ▼
     侧边栏（可隐藏/展开，两边都有）→ 点事件 → 源界面跳转对应时间
            │
            ▼
     事件到证据报告（每事件前后帧 + 解析）
            │
            ▼
     测试记录（三源日志引用 + 事件库）→ Run 页面可加载回放
```

### 1.2 关键设计点

1. **三源完全独立**：各自跑规则，互不等待、互不依赖、不互相解锁。
2. **上报总事件**：某规则命中且声明「上报总事件」→ 往事件驱动记一条 `{时间, 事件名, 来源, 锚点}`。
3. **事件驱动 = 纯记录**：不做判定、不驱动流程、不做逻辑。
4. **时间点语义（用户澄清）**：
   - 总事件表只存**一个时间点** = **上报方的精确时间**。
   - 这个时间点**对上报方精确到行/帧**（日志行号 / 帧序号）。
   - **对其他界面只是近似**（只按时间跳转，可能对不上精确行/帧）。
5. **不耦合**：三源各自独立，缺哪个源（日志被移动/不存在）不影响其他源。

## 2. 需求清单（功能点，供评审）

### FR-R1 事件驱动记录（核心）
- R1.1 三源（loghooks/listener/simcon）命中规则后可上报总事件。
- R1.2 总事件结构：`{seq, event_type, event_name, source, time, anchor}`。
  - `anchor` 是上报方的定位锚点（精确到行/帧/步骤）。
- R1.3 事件驱动只记录，不做判定/逻辑/流程驱动。
- R1.4 落 SQLite 持久化。

### FR-R2 三套可加载 JSON 规则
- R2.1 **日志规则**：复用现有 loghooks `rules/*.json`。
- R2.2 **侦听台规则**（新增 `rules/listener/*.json`）：匹配**帧字段 + 指定内容**（如 `cco 地址`、`字段=分钟采集上报`、`tei==1`），命中 → 上报事件。
- R2.3 **集中器规则**（新增 `rules/simcon/*.json`）：**基于现有用例（task）**，规则可声明 `event` 字段，触发时上报进总事件驱动；不新增独立流程。
- R2.4 三套规则均**可加载**（Run 界面选择/加载）。

### FR-R3 结束条件
- R3.1 **自动结束**：有结束条件（如「集中器用例必须跑完」）→ 以用例为主，跑完即结束。
- R3.2 **默认时间结束**：无成功要求时只做匹配 → 出报告；默认 **10 分钟**（可改动）。
- R3.3 结束条件可配置：`结束方式 = 自动(用例) | 规定时间`，默认时间可改。

### FR-R4 侧边栏（module_log + listener 都有）
- R4.1 左侧**可隐藏/展开**的侧边栏，列总事件。
- R4.2 按**分钟分组**（每分钟一个可展开节点）。
- R4.3 点击事件 → 跳转：
  - 本界面上报（source 匹配）→ **精确跳转**（module_log 到 `file:line`，listener 到 `sequence`）。
  - 他界面上报 → **按时间近似跳转**（module_log 按日志时间、listener 按 log_time）。
- R4.4 实时刷新：后端事件总线 → 前端 **SSE/轮询**，**自动刷新 + 手动刷新**，刷新速度不过快（可配置间隔）。

### FR-R5 报告（事件到证据）
- R5.1 报告 = **事件到证据**：以总事件为骨架。
- R5.2 每个事件附**该源前后（before/after）的帧 + 对应解析**。
  - **日志（module_log）**：前后 **3 帧**（日志行前后 3 行）。
  - **侦听台（listener）**：前后 **2 秒**时间窗内的帧 + 解析。
- R5.3 报告可浏览/导出，供回放分析。

### FR-R6 测试记录（回放）
- R6.1 一次运行 = **三者交互日志引用 + 事件记录 SQLite** 打包为一个**测试记录**。
- R6.2 默认命名：**时间 + 三规则**（如 `20260818-101530_日志规则_侦听规则_集中器规则`；某类无规则写「无」）。
- R6.3 Run 页面可**加载测试记录**：同步加载三源日志（引用）+ 总事件库。
- R6.4 **不耦合**：哪个模块日志文件被移动/不存在 → 不加载对应项；没有对应项就不加载；有才加载。

## 3. 架构设计

### 3.1 数据流总览

```text
┌─────────────────┐  ┌──────────────────┐  ┌───────────────────────┐
│ module_log      │  │ listener          │  │ sim_concentrator      │
│ loghooks 规则   │  │ 帧规则           │  │ 用例(task) + 事件规则  │
│ rules/*.json    │  │ rules/listener/* │  │ rules/simcon/*        │
└────────┬────────┘  └────────┬─────────┘  └───────────┬───────────┘
         │ 上报事件            │ 上报事件               │ 上报事件
         ▼                    ▼                        ▼
        ┌──────────────────────────────────────────────────┐
        │          事件驱动（EventBus/EventStore）          │
        │  总事件表：seq/event_type/event_name/source/      │
        │          time/anchor                             │
        │  SQLite: data/runs/<测试记录>/events.sqlite3     │
        └──────────────────────┬───────────────────────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        module_log 侧边栏   listener 侧边栏   报告(事件到证据)

              └────────────────┼────────────────┘
                               ▼
                        测试记录(路径引用+事件库)

```

### 3.3 数据模型

**总事件**（事件驱动记录，SQLite）：
```text
TotalEvent {
  seq: int,             # 单调递增
  event_type: str,      # 如 meter.collect / sta.minute_report / simcon.onnet
  event_name: str,      # 人读名，如「抄表」「分钟采集上报」「入网」
  source: "log" | "listener" | "simcon",
  time: str,            # 上报方精确时间（日志行时间 / 帧 log_time）
  anchor: {             # 上报方定位锚点（精确到行/帧/步骤）
    log:      { file, line },
    listener: { sequence },
    simcon:   { step_idx },
  },
  run_id: str,          # 归属测试记录
}
```

**测试记录**（manifest）：
```text
TestRecord {
  name: "20260818-101530_日志_侦听_集中器",
  created_at: str,
  rules: { log: [...], listener: [...], simcon: [...] },  # 规则名（无则「无」）
  sources: {          # 只存路径引用，不复制日志
    log:      { path: "LOG/模块/cco/xxx.log", ok: true },
    listener: { path: ".../log_index.sqlite3", ok: true },
    simcon:   { path: ".../task.json", ok: true },
  },
  events_db: "data/runs/<记录名>/events.sqlite3",   # 唯一复制的产物
  end_condition: { mode: "auto" | "time", timeout_min: 10 },
}
```

### 3.4 三套规则结构（草案）

**日志规则**（沿用现有 loghooks，`rules/*.json`）

**侦听台规则**（`rules/listener/*.json`，匹配字段对齐 `minute_reports`/`frames` 真实解析字段）：
```json
{
  "id": "listener.sta_minute_report",
  "source": ["listener"],
  "match": {
    "mode": "minute_report",         // 按分钟采集上报表字段匹配
    "field": "分钟采集上报",          // 事件类别（人读）
    "cco_tei": "001",                // CCO 地址（minute_reports.cco_tei）
    "source_tei": "1",               // TEI（minute_reports.source_tei）
    "station_key": "xx",             // 从节点标识（可选）
    "task_no": 1,                    // 任务号（可选）
    "protocol_type": 3,              // 协议类型 698（可选）
    "meter_type": 1                  // 电表类型（可选）
  },
  "event": {
    "type": "sta.minute_report",
    "name": "STA 分钟采集上报",
    "report": true
  }
}
```
> 匹配字段全部来自 `apps/listener/log_service.py` 的 `minute_reports` 表（`cco_tei`/`station_key`/`source_tei`/`task_no`/`protocol_type`/`meter_type`/`time_seconds` 等）与 `frames` 表（`sequence`/`log_time`/`summary_json`）。锚点 `listener.anchor.sequence` 取 `frames.sequence`。

**集中器规则**（`rules/simcon/*.json`，基于用例 + 事件字段）：
```json
{
  "id": "simcon.onnet",
  "source": ["simcon"],
  "based_on_task": "tasks/anhui_minute_collect.json",
  "event": {
    "type": "simcon.onnet",
    "name": "集中器入网流程完成",
    "report": true
  }
}
```

## 8. AI 验证助手（CLI 优先，2026-08-18 讨论定稿）

> 前述 FR-R1~R6 是「人用」的三源工具（侧边栏/报告/测试记录）。
> 本节是**同一底层、AI 专用**的验证 CLI——AI 开发修改后用来「验证修改是否生效」。

### 8.1 背景：AI 验证修改的痛点

AI 改了代码（如某函数逻辑），但**不知道函数在真实运行中是否被走到**。传统做法是加打印 → 烧录 → 翻日志 → 看命中，步骤分散、费 token。需要一个**声明式验证闭环**：AI 声明「我要验证什么」→ 工具自动匹配 → 拿结构化结论。

### 8.2 决策（用户已定）

| 项 | 决策 |
|---|---|
| **断言语法** | 简化断言 DSL：`verify("pattern", "[MYLOG] xxx")`、`verify_frame(afn=17, fn=232)`，AI 更易写 |
| **结果形式** | JSON 结构化 `{rule_id, hit, count, times, anchors}`；AI 若觉得不够，自己按 anchors 去日志/帧看原始 |
| **触发场景** | CLI 既能触发（调集中器用例 `--trigger task:xxx`）也能纯监听 |
| **烧录** | 独立工具（`flash_and_log` 技能），AI 直接调，验证 CLI **不管烧录** |
| **定位** | 先只做 CLI（不做 UI/侧边栏）；共用底层事件/规则引擎 |
| **范围** | 三源都要（日志/侦听台/集中器） |
| **代码落点** | 独立新包（如 `libs/verify_assistant/`），不碰现有 UI/前端 |
| **后端** | 直连 libs（loghooks 扫日志、simcon runner、listener 帧索引），**无 HTTP 服务依赖** |
| **本轮范围** | 核心 CLI 跑通：断言 DSL + 三源匹配 + 结构化结果 + 触发/监听 + SQLite 记录；测试用单测（假数据/注入） |

### 8.3 CLI 接口（草案）

```bash
# ① 声明断言（可多条，按 name 分组）
verify add mycheck 'verify("pattern", "\\[MYLOG\\] foo called")'
verify add mycheck 'verify_frame(afn=17, fn=232, source_tei="1")'
verify add mycheck 'verify_task(step=4, status="pass")'

# ② 开始监听（三源并行）+ 可选触发集中器用例
verify listen --name mycheck --timeout 120 [--trigger task:anhui_minute_collect]

# ③ 查结果（JSON 结构化）
verify result mycheck
# → {"rule_id":"mycheck","hit":true,"count":2,
#     "times":["10:00:03","10:00:05"],
#     "anchors":[{"source":"log","file":"...","line":42},
#                {"source":"listener","sequence":1088}, ...]}

# ④ 运行记录（测试记录，SQLite）
verify list / verify show <record>
```

### 8.4 断言 DSL → 规则编译

| DSL | 编译成 | 匹配源 |
|---|---|---|
| `verify("pattern", "regex")` | loghooks 文本规则 | 日志（module_log） |
| `verify_frame(afn, fn, source_tei, cco_tei, ...)` | 侦听台帧规则 | 侦听台（listener 帧索引/解析） |
| `verify_task(step, status)` | 集中器步骤规则 | 集中器（simcon runner 步骤结果） |

DSL 编译器把断言编译成三源规则 JSON（复用事件引擎），监听时匹配 → 汇总结构化结果。

### 8.5 与 FR-R1~R6 的关系

- **共用底层**：事件驱动（eventstore/eventbus）+ 三源规则引擎 + 测试记录 SQLite。
- **CLI 先行**（本轮），UI/侧边栏（FR-R4/R5/R6）后续再加。
- **烧录独立**：AI 先用 `flash_and_log` 烧新固件，再调 `verify` 验证。
