# 高频采集失败分析脚本（临时工具，后续可并入台体报文分析扩展）

位于本目录 `_tmp_hf_analyze/`，测试日志已复制到 `_tmp_hf_analyze/测试数据/`（与脚本同目录，整体可独立拷贝）。
复用项目 `libs/parser_lib` / `libs/sim_concentrator.frame_codec`（把 `libs` 加入 `sys.path`），
对台体日志、CCO 日志、侦听台日志做三端交叉分析，定位"某几块表抄读超时不回、补抄超 3 次"的具体失败表与根因。

## 目录结构
```
_tmp_hf_analyze/
├── analyze_taish.py          # 台体日志分析（动作序列/失败表/判定）
├── analyze_cross.py          # CCO + 侦听台交叉分析（二次证据）
├── 高频采集失败分析报告.md    # 本次分析结论（含证据原文）
├── README.md
└── 测试数据/                  # 三份测试日志（CCO/台体/侦听台）
    ├── 01-cco日志/
    ├── 02-台体日志/
    └── 03-侦听台日志/
```

## 时间基准（重要）
三份日志时钟不同步，**时间线一律以侦听台（纯硬件抓包）为基准**：
- 侦听台 HPLC 报文：最准（唯一时间基准）
- CCO 调试日志：基本准，`ApsReadRecord` 为上层处理时刻（比实际到达滞后 30~50s）
- 台体日志：**不可靠**（可能快/慢几分钟），只作为"动作序列"识别（发帧、收 F101、判超时），具体时刻以侦听台/CC"为准

## 依赖
- 项目自带 venv（`ZZT_SELF/.venv/bin/python`，python3.10）或系统 python3
- `libs/sim_concentrator`（frame_codec）、`libs/parser_lib` 可正常 import
- 台体日志为 GBK 编码，CCO 日志为 UTF-8，侦听台报文为 UTF-8 文本

## 用法

### 1. 台体日志分析（动作序列 / 失败表 / 组网成功率 / 最终判定）
```bash
python3 analyze_taish.py "<台体日志路径>"
```
输出：send 采集帧总数、涉及表数、ReadMeter Success/Fail、Recieved F101、busy、
建档案表列表、补抄次数分布、从未 Success 的表（=失败表）、最终判定。

### 2. CCO 日志 + 侦听台日志交叉分析（失败表二次证据）
```bash
python3 analyze_cross.py "<CCO日志>" "<侦听台报文>" <表地址>... \
  [--start 16:42:00 --end 16:44:10] [--cco-only|--sniff-only]
```
输出：
- CCO 侧：目标表命中行数、`ApsReadRecord` 成功回读次数、`aps tx` 发送次数，及具体行
- 侦听台侧：目标表相关 HPLC 帧（请求/应答）及时间
- 判定口径：只有请求帧/aps tx、无 ApsReadRecord/应答数据 → STA/电表未响应；
  大量 retry/队列积压 → 网络拥堵

## 2026-08-20 本次样例结论（供参考）
失败表：`010000012201`、`020000012201`（0x22 网关下挂 698 电表）。
三端证据（以侦听台时间为准）：
- 侦听台：012201 自采集开始（16:42:01）被反复抄读 7+ 次，**持续 ~2.5 分钟无应答**，16:44:48 才首次回读。
- 台体：`read cycle reach max(3)` 后放弃（对应侦听台约 16:44:0x），早于电表回读约 40+ 秒。
- CCO：采集期无 012201 的 `ApsReadRecord`；16:43:55 才向 tei 0022 发送且 tx_cnt 3；回读滞后 30~50s。
根因：**012201（0x22 网关）入网晚（16:23 组网）、采集时响应时延大，台体补抄窗口不足 → 超时判失败；非网络拥堵**（其余 92+ 只表均秒级成功）。
